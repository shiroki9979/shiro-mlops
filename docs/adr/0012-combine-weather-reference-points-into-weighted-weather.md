# ADR-0012：以加權天氣合成多氣象代表點

> - Created: 2026-11-16
> - Last Updated: 2026-11-16

## 1. Context

[ADR-0009](0009-decouple-ml-tasks-via-task-config-and-task-types.md) 讓任務設定承載氣象代表點，並宣告其「可多個、可加權」，但實作時以驗證器限制每個任務只能有一個代表點，加權延後到 M3。全台逐時實際負載的預測對象是全台，三個 ML 任務卻都只讀臺北的天氣；臺中與高雄雖已列入擷取目錄並持續入庫，仍未進入模型。

開放多個代表點後，有幾件事需要一起定義：模型如何看待多個代表點的天氣、權重從哪裡來、部分代表點缺少預報或觀測時如何降級、訓練與 serving 如何維持同一特徵定義，以及 API 如何揭露天氣來源。截至 2026-11-08，可用的推算負載只有約 850 小時，特徵維度的選擇必須顧及小資料下的穩健性。

## 2. Decision

以**加權天氣**（定義見 GLOSSARY.md）作為預測對象的天氣輸入：

- **合成單一值**：`weather.fields` 的每個欄位，依各代表點權重合成一個值。所有欄位共用同一組權重；模型的欄位名稱不變。
- **權重固定於任務設定**：每個代表點的權重大於 0、總和為 1，載入時驗證；單點時權重為 1。初始值由台電區域供需快照的北、中、南三區用電負載占比推算（對應臺北、臺中、高雄），東部占比依比例分給三點，計算期間註記在設定旁。權重只在採用研究證明有改善時，經 PR 修改。
- **降級與無法產出**：每個代表點各自走既有替代鏈（[ADR-0007](0007-isolate-cwa-access-behind-scheduled-ingestion.md)）。只要一點降級，整次預報即為降級預報；任一點連替代資料都沒有，即無法產出預報，不剔除該點、不重新正規化。
- **訓練與 serving 同一定義**：加權由 runner 負責（共用元件，[ADR-0009](0009-decouple-ml-tasks-via-task-config-and-task-types.md)）。觀測天氣在各代表點同一觀測整點皆有值時才合成；任一點缺少的整點沒有加權值，交由各任務類型既有的缺值規則處理。任務類型收到的仍是單一張「時間＋天氣欄位」表，訓練表格式不變。
- **來源依代表點揭露**：API item 的天氣數值為加權值；每個天氣欄位的來源改為「代表點 → 來源」對照。所有任務一律採用此形狀，單點任務只有一個代表點。

### Rationale & Alternatives Considered

- **選定方案：合成單一值、固定權重、嚴格降級**。小資料下維度最低；權重出自專案自有的區域負載資料；訓練與 serving 永遠看到同一個特徵定義。
- **候選方案 A：每個代表點各自成為特徵，由模型學權重**。語意最直接，但約 850 小時資料配上 6 個天氣特徵容易過擬合，API 回傳的天氣數值也失去單一意義。保留為 lab 的後續研究題目。
- **候選方案 B：只加權氣溫，濕度取自主要代表點**。需要新增「主要代表點」概念，且同一任務的天氣欄位會有兩套合成規則。
- **候選方案 C：沿用原 TICKET-301 的 0.45／0.30／0.25**。只寫「人口／用電加權」，沒有可查證的出處。
- **候選方案 D：每次訓練以最近 N 日的區域負載動態重算權重**。不同模型版本的同名特徵定義不同，serving 也必須追蹤當版權重，換得的季節適應性不值得這個成本。
- **候選方案 E：缺點時剔除並以剩餘代表點重新正規化**。模型以三點權重訓練，剔除後特徵定義已改變，卻仍標為正常或降級，會誤導使用者。替代鏈最後一層（同月份同小時歷史平均）在累積一個月觀測後幾乎必定存在，嚴格規則實際觸發 503 的機率很低。
- **候選方案 F：單點任務維持舊的來源形狀，只有多點任務改**。消費端需依任務分辨兩種形狀；目前唯一的 API 消費端（前端）不讀來源欄位，統一形狀的成本最低。
- **候選方案 G：訓練表保留逐點觀測，各點依任務類型的對齊規則對齊後再加權**。三個任務類型對齊觀測天氣的規則各不相同（兩小時內向後對齊、時間精確對上、有上限的向前補值），採用此方案須同時改動 `TrainingData` 介面、訓練表格式、三個任務類型與 lab 回測。改由 runner 在整點上加權，單點任務的結果與加權前完全相同。代價是 lab 無法用同一份訓練表快照比較不同權重，須另建原始資料層的快照。

## 3. Consequences

- **正面效益（Positive）**：
  - 全台預報的天氣涵蓋北中南三區，權重有可追溯的資料出處。
  - 訓練、serving 與 lab 快照共用同一特徵定義；逐點來源讓降級原因可以追溯到單一代表點。
- **代價與風險（Trade-offs & Risks）**：
  - 三個測站缺漏時段的聯集大於單一測站，可用的訓練列會減少；採用研究須揭露損失量。
  - 代表點越多，任一點完全無資料而回傳 503 的機會越高。
  - API 的天氣來源欄位對所有任務都是破壞性變更；Feast 天氣 view 改存加權天氣。
  - 某點缺一個觀測整點時，該整點沒有加權值，即使其他點有值；遞迴回歸會以兩小時內較早的加權值補上，直接分類則捨棄該小時。
  - 訓練表只保存加權後的天氣，lab 比較不同權重時須自建原始資料層的快照。
- **不做／延後範圍（Out of Scope / Deferred）**：
  - 逐點天氣特徵、隨時間重算的權重、東部氣象代表點。
  - 高負載預警與用電型態異常偵測的採用，兩者各自需要回測基線。

## 4. Compliance

- 任務設定載入測試：權重總和不為 1、權重小於或等於 0、引用不存在的代表點，皆須於載入時失敗。
- Serving 測試：一點降級時整次為降級預報；一點無任何替代資料時無法產出預報；三點正常時數值等於權重加總。
- 一致性測試：訓練與觀測 serving 經同一 runner 加權；任一點缺少的整點沒有加權值；加權後的訓練表往返無損。
- Code Review 清單：不得在缺點時以剩餘代表點重新正規化；不得在任務設定以外寫死權重。
