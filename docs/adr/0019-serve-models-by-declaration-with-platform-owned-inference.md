# ADR-0019：模型隨附宣告說明自己的輸入與產出，預測程式留在平台並依宣告執行

## Plain Language Summary

現在每一種預測工作的設定檔同時決定怎麼訓練模型，以及上線時要替模型準備哪些輸入；設定檔又包在平台程式裡，所以研究者每換一組輸入、每多一種預測工作，都得改平台程式並重新部署。因此決定讓每一份訓練好的模型隨附一份說明，寫明它需要哪些輸入、怎麼算特徵、產出什麼；預測程式仍放在平台並照這份說明執行，模型本身不帶任何程式。預測工作的身分改由它對外承諾的產出來定義，設定檔搬到平台程式之外。代價是既有三種預測工作都要改寫成新格式，平台要多維護特徵、輸入與產出三份清單，而且新增一種模型做法時仍要改一次平台程式。

## 1. Context

M11 要讓**研究者**交出**模型交付包**，由平台服務（用語見 [GLOSSARY.md](../../GLOSSARY.md)「6. ML 任務」）。成本目標是：新增 **ML 任務**時若沿用已註冊的任務類型，平台程式（`src/`）不必改；新增任務類型時，只需要一次有邊界、審過就不必再動的平台端變更。[ADR-0009](0009-decouple-ml-tasks-via-task-config-and-task-types.md) 的「任務設定 + 任務類型」做不到這一點，原因有五個：

- **任務設定同時是訓練配方與 serving 的輸入需求**。`[params]` 與 `[weather]` 決定平台怎麼訓練，也決定 serving 要讀多長的歷史、哪些天氣欄位。模型實際用的配方另存在模型目錄裡，兩邊不一致時只能拒絕載入並要求重訓。在研究空間訓練好的模型，配方只要和任務設定不同就無法服務。
- **任務設定放在 `src/` 內，隨映像發布**。新增一份任務設定算一次 `src/` 變更，還要重建 API 映像。
- **任務類型同時負責訓練、保存、載入與預測**，程式裡還有會隨研究改變的常數（例如預警的機率門檻與最大提前時數）。這些數值一改就要改 `src/`。
- **回應 schema 由任務類型決定**，而且會依任務的天氣欄位動態長出欄位。研究者改了天氣輸入，下游看到的形狀就跟著變。
- **ML 任務綁死一個任務類型**。換估計器要改任務設定並重新部署，[ADR-0011](0011-co-locate-lab-workspace-with-unidirectional-dependency.md) 還要求每次更換都另立 ADR。

核心問題是：哪些東西屬於 ML 任務的身分、哪些屬於某一份模型、哪些屬於平台程式，三者的界線要重新劃定。

## 2. Decision

推論程式與特徵轉換程式留在平台；每一份模型隨附一份**宣告**，平台依宣告服務它。ML 任務的身分由**輸出契約**定義，不再綁定單一任務類型。本節只記決策；宣告的欄位、規則代碼與任務設定 schema 的草案見[研究空間契約 §6](../reference/lab.md#6-m11-契約草案尚未實作)。

### 2.1 成品：一個目錄加一份宣告

- **同一種成品格式**：模型交付包與平台訓練的結果都是一個目錄，內含一份宣告檔與任務類型的原生模型檔，兩者只以宣告裡的出處種類（平台或交付）區分。成品的身分是模型目錄的 SHA-256。
- **宣告的內容**：身分（格式版本、所屬的 ML 任務、輸出契約、任務類型）、特徵配方、輸入宣告（序列、天氣欄位、氣象代表點與權重、預報或觀測）、任務類型參數（模型的操作點，例如預警機率門檻）、支援的最大時程、訓練截止、出處。交付包的出處是**研究出處**。
- **可以推導的不宣告**：serving 要讀多長的歷史、歷史要多完整，一律由任務類型從特徵配方推出，不另外寫進宣告。
- **宣告只含資料**：成品不帶推論程式、特徵程式或預先算好的特徵。

### 2.2 任務類型是註冊單位，推論端由宣告參數化

- **歸屬**：推論程式與特徵轉換程式都在 `src/`。宣告指名一個已註冊的任務類型，平台在同一個行程內依名稱找到它的推論端來載入與預測。
- **註冊單位**：一個任務類型包含預測策略、估計器、特徵解譯與產出。換估計器就是新的任務類型。「預測策略 × 估計器」的兩軸拆分，等第二種估計器真的要接上既有策略時再評估。
- **審過就不必再動**：推論端的行為完全由宣告決定，程式裡只保留定義任務類型語意的部分。現有推論端服務不了的成品，在**可服務檢查**時拒絕，不修改推論端去遷就。
- **格式的寫入與讀取都在 `src/`**：研究空間的訓練程式呼叫 `src/` 的寫入函式產生交付包，格式只有一份定義。
- **平台訓練是選配**：任務類型可以只提供推論端。它的訓練程式放在 `lab/` 的常設模組，使用 `src/` 的特徵程式與寫入函式。
- **新任務類型進入平台的路徑**：研究者開 PR 把推論端（訓練端選配）搬進 `src/`，由**平台維護者**審查。邊界由所有已註冊任務類型共用的一致性測試強制，不必各立一份 ADR。
- **既有三個任務類型在 M11 內改用新契約**，平台訓練的結果也寫出同一種宣告。

### 2.3 三層形狀契約：名稱即契約，只增不改

成品的輸入輸出形狀分三層，每層各有一份放在 `src/` 的具名清單：

- **特徵配方**的詞彙：宣告能引用的特徵種類。任務類型宣告自己能解譯哪些種類。
- **輸入目錄**：平台能供應的原始輸入。只收整條 serving 路徑（預報、**預報版本回退**與降級）都存在的項目，有入庫不等於在目錄裡。
- **輸出契約**：ML 任務對下游承諾的產出。

三層共用同一個版本化原則：名稱一旦被平台存放的成品引用，語意就不再改；要改語意就用新名稱；都不設整體版本號。宣告檔的結構另有格式版本，推論端必須能載入平台存放的成品用到的每一個格式版本。設計理由、情境對照與被否決的做法見[三層形狀契約說明](../explanation/three-layer-handoff-shape-contract.md)。

### 2.4 輸出契約是 ML 任務的身分

- **ML 任務綁輸出契約，不綁任務類型**。任務設定指名 ML 任務的輸出契約，成品的宣告指名自己產出的契約，兩者相同才可服務。任務類型不同的成品，只要產出同一份契約，就能服務同一個 ML 任務。
- **輸出契約定義的內容**：
  - 產出的欄位、單位與語意；
  - 承諾的時程範圍；
  - 標籤的定義，例如**高負載門檻**；
  - 評分器與**核心指標**；
  - 沒有對手可比時用的 naive 基準；
  - 監控用的健康判定規則，門檻數值仍寫在任務設定。
- **不因任務類型而異**：同一個 ML 任務的每一份模型都以同一套規則評分與判定健康。任務類型訓練時自己算的指標只作診斷。
- **相容與破壞**：相容擴充只有新增選填欄位。刪改欄位、改單位或語意、改時間粒度、改**預測對象**、縮短時程範圍都是破壞性變更，要開新的輸出契約與新的 ML 任務；同一個 ML 任務不會中途換契約。
- **天氣回聲改成固定形狀**：回應裡的天氣輸入改放在形狀固定的物件，輸入怎麼改，回應 schema 都不變。
- **下游不在 M11 一般化**：**已發布預報**、**預報實績**與**預報檢視**仍綁定動態視界預報。

### 2.5 輸入需求取自現役模型的宣告

serving、就緒檢查與 smoke check 的輸入需求，一律從**現役模型**的宣告推出。氣象代表點、權重與天氣欄位由成品的宣告提供，不屬於 ML 任務的身分。任務設定裡的訓練配方只用於平台訓練。

### 2.6 任務設定搬出平台程式

- **位置**：任務設定放在 repo 根目錄、`src/` 之外的 `tasks/<task_id>.toml`，以 PR 修改。它和 [ADR-0020](0020-hand-off-trained-models-and-pin-the-serving-model.md) 的期望狀態檔並列但不合併，因為任務設定要重啟才生效，期望狀態則會熱生效。
- **內容**：頂層是 ML 任務的身分（識別、預測對象、目標、輸出契約）與監控設定。平台訓練用的欄位收進一張選填的表；沒有這張表的 ML 任務只能靠**釘選**上線。
- **`task_id` 即身分**：不支援改名，改名等於移除舊任務、新增一個新任務。
- **API 與 Dagster 都執行掛載的工作樹程式**，映像只提供正式相依。工作樹的正式相依和映像建置時不一致，就啟動失敗並要求重建映像。
- **成本指標**：沿用已註冊的任務類型新增 ML 任務時，0 個 `src/` 變更、0 次映像重建。「重新部署」定義為重建映像；重啟 API 與重新載入 Dagster 不算。
- **任務集合不做熱載入**：任一份任務設定無效，API 與 Dagster 都啟動失敗。

### 2.7 可服務檢查

- **一份程式**：可服務檢查是 `src/` 的純函式。研究空間交付前的預檢與平台的正式檢查共用它，只有平台的結果算數。
- **三段**：靜態檢查（宣告的 schema、任務類型、輸出契約、特徵種類、輸入目錄、時程範圍、訓練截止、檔案白名單與大小上限）、載入、以合成輸入試推論。前一段失敗就不進下一段。
- **只問能不能服務**：試推論不用真實資料；比好壞是**評估閘門**的事。
- **回報**：靜態檢查一次列出全部違規，每條帶規則代碼。未通過不是終局判定，修正後重新交付即可。
- **平台訓練的結果也要通過**，用來攔下平台端的偏差。

### Rationale & Alternatives Considered

- **取捨一：推論程式與特徵程式歸誰**
  - **選定方案：歸平台，成品只帶宣告與非執行格式的模型檔**。平台不執行交付者的程式，[ADR-0010](0010-persist-models-in-native-non-executable-formats.md) 的信任邊界不必放寬；特徵程式只有一份，研究與 serving 不會分叉。
  - **候選方案 A：交付包自帶推論程式**（MLflow pyfunc、models-from-code）。等於在平台執行研究者的程式，那段程式也不受 `src/` 的 CI 與審查約束。未採納。
  - **候選方案 B：通用格式 runtime**（ONNX、Treelite）。只解決載入與單步預測，遞迴展開與特徵組裝仍要平台自己寫，相依也大。未採納。
  - **候選方案 C：外部 serving 系統**。預測輸入關卡仍留在平台，等於多維運一個服務。未採納。
  - **候選方案 D：交付包帶預先算好的特徵**。serving 要從最新的負載歷史即時計算，做不到。未採納。
- **取捨二：註冊單位與 ML 任務的綁定**
  - **選定方案：註冊任務類型，ML 任務綁輸出契約**。換估計器不必動任務設定，釘選期間平台模型也不必跟著換任務類型。
  - **候選方案 E：「預測策略 × 估計器格式」兩軸註冊**。跨策略的估計器介面還沒有實例可以驗證。延後。
  - **候選方案 F：ML 任務綁死一個任務類型**。換估計器就要改任務設定並重新部署。未採納。
- **取捨三：成品格式**
  - **選定方案：平台模型與交付包共用同一種格式**。可服務檢查、評估閘門、載入與雜湊只有一條路徑。
  - **候選方案 G：平台模型沿用現行格式**。推論端要維護兩種格式。未採納。
  - **候選方案 H：在宣告裡寫出歷史長度與完整度**。與配方各存一份，會重演任務設定與模型配方不一致的問題。未採納。
  - **候選方案 I：研究空間依文件規格自行寫檔**。格式會有兩份定義，偏差要到可服務檢查才會發現。未採納。
- **取捨四：版本化**
  - **選定方案：名稱即契約，只增不改**。推論端只需保證平台存放的成品引用的每個名稱都還在。
  - **候選方案 J：每層一個整體版本號**。平台得保有每一版的完整實作。未採納。
  - **候選方案 K：同一個 ML 任務內升輸出契約的主版本**。同一個識別下會混雜兩種形狀，預報實績也失去可比性。未採納。
  - **候選方案 L：承諾載入所有曾經通過可服務檢查的成品**。支援期沒有上限。未採納。
- **取捨五：任務設定的位置與程式來源**
  - **選定方案：repo 根目錄，API 改跑工作樹程式**。任務設定經過審查、有歷史；程式與任務設定由同一個 commit 決定。
  - **候選方案 M：留在 `src/`，改指標的算法**。API 映像仍要重建。未採納。
  - **候選方案 N：放在資料目錄**。沒有審查，也沒有歷史。未採納。
  - **候選方案 O：與期望狀態檔合併**。生效方式不同的欄位混在同一份檔案裡。未採納。
  - **候選方案 P：任務集合熱載入**。要把 OpenAPI 回應型別與 Dagster definitions 都改成動態，代價和新增 ML 任務的頻率不成比例。未採納。
  - **候選方案 Q：API 繼續跑映像程式**。映像程式可能不認得工作樹裡新任務設定引用的任務類型。未採納。
- **取捨六：評分與健康判定的歸屬**
  - **選定方案：歸輸出契約**。交付包的任務類型可以和平台模型不同，比較依據不能由任何一方的任務類型提供。
  - **候選方案 R：留在任務類型**。同一個 ML 任務換了模型就換了評分與健康規則。未採納。

## 3. Consequences

- **正面效益（Positive）**：
  - 沿用已註冊的任務類型時，改特徵配方、代表點與權重、模型操作點都只要重新交付；新增 ML 任務只要兩份設定檔與一次重啟。
  - 模型實際用的配方就是 serving 的輸入需求，兩者不再各存一份。
  - 評分、健康判定與回應形狀都由輸出契約決定，同一個 ML 任務換模型後仍可比較。
  - 新任務類型的邊界由共用的一致性測試強制，不依賴個別審查的仔細程度。
- **代價與風險（Trade-offs & Risks）**：
  - 既有三個任務類型都要改寫，平台模型要各重訓一次才有新格式的成品。
  - 回應裡的天氣回聲改形狀，是對 API 消費者的破壞性變更，工程主控台要配合修改。
  - serving、就緒檢查與 smoke check 都要先解析出現役模型，才能計算輸入需求。
  - 新增任務類型仍要一次 `src/` PR；帶新相依時還要重建映像。
  - 新增或下架 ML 任務要重啟 API 並重新載入 Dagster。
  - 新的特徵種類、新的輸入目錄項目、輸出契約的新欄位各要一次 `src/` PR；平台要維護三份清單與每個格式版本的黃金 fixture。
- **不做／延後範圍（Out of Scope / Deferred）**：
  - 「預測策略 × 估計器」兩軸註冊。
  - 下游（已發布預報、預報實績、預報檢視）一般化到其他輸出契約。
  - 全新資料來源的擷取，以及研究者自帶外部資料。
  - 訓練是否改用預報天氣。
  - 新任務類型的套件怎麼進入正式相依、API 與 Dagster 的相依是否拆開，留給實作票。

## 4. Compliance

- 一致性測試：每個已註冊的任務類型都通過同一套測試：保存後再載入的預測一致、只寫入非執行格式、輸出符合它宣告的輸出契約、輸入需求取自宣告。
- 黃金 fixture：平台存放的成品用到的每個格式版本，都在 `tests/fixtures/` 有一份成品，由一致性測試逐一載入並預測。
- 可服務檢查的單元測試：每個規則代碼各有一份會觸發它的 fixture；靜態檢查一次回報全部違規。
- 任務設定的離線測試：每份 `tasks/*.toml` 通過驗證且 `task_id` 等於檔名；任務設定與期望狀態檔一對一；沒有平台訓練表的 ML 任務不得開啟自動訓練，也不得沒有釘選。
- 啟動檢查的單元測試：工作樹的正式相依匯出與映像記錄的雜湊不一致時，API 與 Dagster 啟動失敗。
- 慣例檢查：`lab/` 只能經 `src/` 的寫入函式產生成品；`src/` 不得 import `lab`（沿用 ADR-0011）。
- Code Review 清單：任務類型的程式不得有會隨研究改變的常數；特徵、輸入目錄與輸出契約已被引用的名稱不得改語意。
