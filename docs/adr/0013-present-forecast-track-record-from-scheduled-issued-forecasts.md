# ADR-0013：預報檢視以定時發布的預報實績呈現歷史表現

## 1. Context

預報檢視的 `/history` 頁面目前顯示前端合成的假資料：誤差指標、尖峰命中率、時序圖與結論文字都寫死在前端，且沒有任何資料請求。系統也沒有正式的歷史表現產生者：

- `POST /predict` 以請求當下為 `as_of` 隨需計算，回應後即丟棄；資料庫只有入庫資料表，沒有保存預報的表。
- `{task_id}__monitoring` 判斷的是訓練當時驗證集上的單步誤差，不是預報與事後實際負載的對照。
- 唯一的多步誤差評估是 `lab/` 的滾動起點回測。`src/` 不得 import `lab`（[ADR-0011](0011-co-locate-lab-workspace-with-unidirectional-dependency.md)）；回測以實測天氣代替預報天氣，結果不代表正式 serving 誤差；截至 2026-11-08 的研究只有 2 個評估起點。

M4 要把預報檢視公開上雲（[GitHub #123](https://github.com/shiroki9979/shiro-mlops/issues/123)），必須決定 `/history` 的資料由誰產生、呈現什麼。全台逐時實際負載無法回補（[ADR-0008](0008-derive-hourly-actual-load-from-regional-snapshots.md)），不論採用哪種做法，上線初期可用的資料都很少。

## 2. Decision

`/history` 呈現**預報實績**，不呈現回測。預報實績由**已發布預報**對照全台逐時實際負載而得（定義見 GLOSSARY.md），兩者都由 `src/` 在地端產生。

### 2.1 已發布預報

- **定時發布**：地端 Dagster 資產每小時發布一份動態視界預報，視界 $H = 168$，以發布時刻為 `as_of`。降級預報與負載起點過舊的既有規則照常適用（[ADR-0007](0007-isolate-cwa-access-behind-scheduled-ingestion.md)）。
- **不可變、永久保存**：發布後原樣保存於地端，不更新、不刪除，也不以事後重新預報回補。每份記下發布時刻、負載起點、運行狀態（正常或降級）與模型版本識別。
- **模型版本識別不依賴 MLflow**：MLflow 不可用時仍須有可追溯的識別，例如訓練完成時刻或模型檔雜湊；MLflow 的模型版本另作附註。具體識別方式於實作工單定義。
- **只有定時發布才算**：隨需的 `/predict` 不寫入已發布預報。
- **照常發布**：模型健康檢查為 `WARNING` 時照常發布。無法產出預報（例如負載起點過舊）時，該時點不發布、事後也不補發。

### 2.2 預報實績

- **地端計算**：已發布預報與全台逐時實際負載都在地端，彙整結果隨匯出管線送上雲。通道由[預報檢視的服務形態與新的混合雲邊界](https://github.com/shiroki9979/shiro-mlops/issues/127)決定。
- **提前時數自發布時刻起算**：提前時數為目標小時減發布時刻；目標小時不晚於發布時刻的步數不計入。
- **計入範圍**：只在同時有已發布預報與有效逐時觀測的目標小時計算誤差。降級預報照常計入，不分開統計。未能發布的時點與缺值的小時不計入，也不在預報檢視揭露。

### 2.3 預報檢視的最低呈現內容

- **統計期間**：最近 30 天的滾動窗，依目標小時是否落在窗內判斷。
- **指標卡**：MAPE 與 MAE 各一張，標題數字固定取提前 24 小時。
- **提前時數曲線**：MAPE 對提前時數 1–168 小時，每個提前時數一點；MAE 放在 tooltip。
- **時序圖**：統計期間內實際負載與提前 24 小時已發布預報的對照。
- **累積不足**：有已發布預報且有有效逐時觀測的目標日未滿 7 天時，只顯示空狀態與「已累積 N 天」，不顯示指標。
- **公開欄位**：目標小時、全台逐時實際負載、提前 24 小時的預報值、各提前時數的 MAPE 與 MAE、累積天數。不揭露運行狀態、天氣來源、模型版本與資料缺口。
- **移除**：尖峰命中率、RMSE、寫死的結論卡、沒有出處的基準值、模型名稱與「滾動回測」字樣。

### Rationale & Alternatives Considered

- **選定方案：定時發布、地端計算預報實績**。公開頁面的數字是系統在營運中真正說過的話，可以稽核。發布越早開始，累積越早開始。
- **候選方案 A：由 `lab/` 匯出回測結果作靜態展示**。回測以實測天氣預報，數字比營運表現樂觀；評估起點很少；`src/` 不能 import `lab`，只能人工匯出，無法自動更新。回測的用途是比較候選模型，不是營運紀錄。
- **候選方案 B：在 `src/` 新增正式的滾動起點回測資產**。仍是模擬重新預報，每次重新訓練都會改變過去的數字；且須把回測邏輯從 `lab/` 移入 `src/`。
- **候選方案 C：顯示示意資料，或延後到上雲之後**。公開頁面的假資料即使標示也會削弱可信度；發布越晚，預報實績越晚開始累積，且無法回補。
- **候選方案 D：把每次隨需請求記錄為已發布預報**。樣本取決於誰在何時請求，有偏誤；雲端也未必提供隨需推論。
- **候選方案 E：提前時數自負載起點起算**。與 `lab/` 的步數一致，但會把發布時已經過去的小時算作預報，使短提前時數的誤差偏低。
- **候選方案 F：排除降級預報，或在模型健康檢查失敗時暫停發布**。兩者都會讓預報實績避開表現較差的期間，美化數字。健康檢查依據的是訓練當時的驗證誤差，不適合決定是否發布。
- **候選方案 G：標題數字合併所有提前時數**。最容易與最難的預報被平均在一起，數字會隨 $H$ 改變。提前 24 小時對應日前預測的慣例，觀眾容易理解。
- **候選方案 H：每日或每 6 小時發布**。樣本累積速度只有每小時發布的 1/24 或 1/6；每小時發布的保存量約每年 150 萬列，成本可忽略。

## 3. Consequences

- **正面效益（Positive）**：
  - 預報檢視的歷史表現有正式且可稽核的產生者，與資料送上雲的通道無關。
  - 已發布預報的語意與 [GitHub #124](https://github.com/shiroki9979/shiro-mlops/issues/124) 的結論一致（以發布時刻為 `as_of`），可供 #127 作為預報檢視「目前預報」的來源。
  - 每份已發布預報都可追溯到模型版本，工程主控台日後可依版本或運行狀態分析。
- **代價與風險（Trade-offs & Risks）**：
  - 新增已發布預報的保存與兩個地端資產；地端工作站每小時多一次 168 步遞迴推論。
  - 開始發布後至少 7 天，`/history` 只有空狀態；擷取中斷越多，可用樣本越少。
  - 公開頁面的提前時數與 `lab/` 的步數不可直接比較。
  - 公開數字混合多個模型版本與運行狀態，無法在預報檢視上歸因。
  - 若 #127 讓 `/` 顯示隨需預報而非最新一份已發布預報，`/` 與 `/history` 的數字將來自不同來源。
- **不做／延後範圍（Out of Scope / Deferred）**：
  - 比較基準（例如季節性天真預報）：須另行定義，並與已發布預報區分。
  - 依模型版本分段、降級預報分析與發布涵蓋率：屬工程主控台。
  - 高負載預警與用電型態異常偵測的預報實績。
  - 資料送上雲的通道與雲端副本的保存規則。

## 4. Compliance

- 已發布預報測試：寫入後不可更新；隨需 `/predict` 不寫入；無法產出時該時點沒有紀錄；MLflow 不可用時仍有模型版本識別。
- 預報實績測試：提前時數不大於 0 的步數不計入；缺少有效逐時觀測的目標小時不計入；降級預報計入；30 天窗依目標小時判斷；累積未滿 7 天時不產出指標。
- Code Review 清單：不得以事後重新預報回補或覆寫已發布預報；預報檢視不得揭露運行狀態、資料缺口與模型版本；`/history` 不得使用「回測」稱呼預報實績。
