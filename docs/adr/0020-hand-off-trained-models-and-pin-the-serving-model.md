# ADR-0020：研究者交出訓練好的模型，平台檢查並比較後，由人以 PR 指定哪一份上線

## Plain Language Summary

平台每天自動重新訓練並直接換上新模型，沒有人檢查；研究者在研究空間訓練出更好的模型，卻沒有正式的路可以讓它上線。因此決定研究者交出訓練好的模型成品，平台先確認它能被服務，再用最近的真實資料和目前上線的模型比較，贏了才可以由人透過審查過的設定檔指定它上線；每天的自動重訓同樣要比贏才會更新，而且不會蓋掉人指定的那一份。出問題時可以改回任何一份上線過的模型，不必重新比較。代價是平台要多存好幾份模型和一組只增不改的紀錄，換模型要靠一個持續核對的背景程序才會生效，主機也改成只跑發布分支、由人手動更新。

## 1. Context

M11 要讓**研究者**交出**模型交付包**，由平台把關後上線（用語見 [GLOSSARY.md](../../GLOSSARY.md)「6. ML 任務」）。研究者與**平台維護者**目前可以是同一人，但契約按兩個人設計，不依賴默契；邊界以型別、測試、CI 與審查在同一個 repo 內強制。[ADR-0019](0019-serve-models-by-declaration-with-platform-owned-inference.md) 已決定成品的格式與**可服務檢查**，本 ADR 決定成品怎麼成為**現役模型**。現況有四個缺口：

- **重訓即上線**。排程重訓的結果直接覆蓋模型目錄，沒有任何比較；產出會公開在**預報檢視**上。
- **研究結論只能以配方採用**。[ADR-0011](0011-co-locate-lab-workspace-with-unidirectional-dependency.md) 的採用路徑是修改任務設定的訓練配方，再由平台重訓。研究空間訓練好的模型本身不能上線，平台不支援訓練的估計器也就無法服務。
- **換模型要重啟**。API 只在啟動時載入模型，重訓後要手動重啟；重啟之前 API 與 Dagster 用的是不同的模型。
- **主機跑的是開發分支**。地端主機就是開發用的機器，Compose 掛載的 checkout 切到哪個分支，正式的 run 就跑哪個分支的程式；`main` 長期落後 `dev`。

[ADR-0010](0010-persist-models-in-native-non-executable-formats.md) 的「不載入可執行格式」只規範平台自己訓練的模型，沒有精確定義，完整性雜湊也列為延後。交付包來自平台之外，這條邊界要重新寫明。

## 2. Decision

研究者交付已訓練的成品；平台以可服務檢查與**評估閘門**把關；人以 PR 修改期望狀態來**釘選**；平台核對後才生效。本節只記決策；檔案 schema、資料表、規則代碼與指令的草案見[研究空間契約 §6](../reference/lab.md#6-m11-契約草案尚未實作)。

### 2.1 交付的是成品，不是配方

- 研究者交出訓練好的模型交付包，平台通過把關後直接服務它，不重訓。
- 交付包帶**研究出處**，不帶評估證據。研究出處指向的 commit 必須已合併進 `dev`，交付時由主機檢查。
- 訓練截止由 `src/` 的寫入函式從訓練資料推導，研究者不手寫；工作樹有未提交變更時拒絕寫出。

### 2.2 現役模型、平台模型與排程重訓

- 每個 **ML 任務**一次只有一個現役模型：有釘選時是釘選的模型版本，否則是**平台模型**。
- 排程重訓保留，但只更新平台模型，永遠不覆蓋釘選。釘選期間照常重訓，平台模型待命。
- 平台訓練是選配。沒有平台訓練的 ML 任務只能靠釘選上線，不得解除釘選。
- 自動訓練開關只控制排程要不要訓練，與釘選彼此獨立。
- 釘選不會到期。釘選的模型版本要不要更新，由人負責：交付包由研究者重新交付，平台出處的釘選由平台維護者決定；平台只負責讓新舊看得見。

### 2.3 評估閘門

- **有拘束力**：現役模型的更替一律先過評估閘門，判定不得人工推翻。平台訓練的結果（**候選模型**）和平台模型比，勝出才成為新的平台模型；交付包和現役模型比，通過才可以釘選。解除釘選與**退回**不經過閘門。
- **判定一律由平台重算**：平台讓成品走標準推論路徑，以**輸出契約**的評分器與**核心指標**評分。交付包附上的任何評估結果都不採信。
- **評估窗**：起點取雙方訓練截止中較晚者之後的最近 14 天，照 [ADR-0018](0018-access-research-data-through-data-freezes-and-knowledge-time.md) 的標準回測規則以**知悉時間**取輸入。資料不足判待定，候選模型不取代對手，資料足夠後自動重評。
- **勝出規則**：平台訓練的結果採不劣於，容忍幅度依 ML 任務設定，預設 5%；交付包必須嚴格優於現役模型。核心指標只在雙方都能產出預測的起點上計算，候選模型能產出預測的起點比例不得低於對手。監控用的絕對門檻不參與閘門。
- **冷啟動**：沒有對手時，改和輸出契約定義的 naive 基準比。
- **判定以成品的 SHA-256 為鍵**：位元組相同的成品不重跑閘門；落敗是終局，要再挑戰就得交出內容不同的成品。
- **過時的通過判定不算數**：通過的判定只在判定時的對手仍是目前要取代的對象時才有效，交付包與平台訓練的結果都適用。
- **驗證窗固定 14 天**：平台訓練保留的驗證窗由比例改為固定 14 天，與評估窗一致。
- **平台訓練的結果先過可服務檢查，才進閘門**。可服務檢查未通過算 run 失敗；閘門落敗或待定是正常結果。

### 2.4 期望狀態在 repo，平台紀錄在資料庫

- **期望狀態**：每個 ML 任務一份放在 repo 內、`src/` 之外的宣告檔，內容只有釘選的模型版本與自動訓練開關，以 PR 修改。CI 只檢查能在 repo 內查證的項目。
- **平台紀錄**：交付、可服務檢查報告、閘門判定、生效四種紀錄，放在資料庫的 append-only 資料表，以成品的 SHA-256 為鍵。MLflow 與 Dagster metadata 照常寫，但不是權威來源。
- **核對後才生效**：一個持續執行的核對程序（reconciler）讀取期望狀態，驗證通過才寫一筆**生效紀錄**。釘選要生效，成品必須在存放區且雜湊相符、通過可服務檢查，並且有仍然有效的通過判定，或符合 §2.5 的退回資格。
- **兩個行程讀同一筆生效紀錄**：API 輪詢生效紀錄並熱替換模型，不必重啟；Dagster 的發布讀同一筆。每一筆產出都帶著它實際使用的模型 SHA。
- **期望無效時不生效**：不寫新的生效紀錄，舊的現役模型繼續服務，smoke check 判失敗，監控判 `WARNING` 並附上拒絕理由。系統不替人改回平台模型，也不關閉服務。
- **不設繞過 git 的開關**：期望狀態要等主機的工作樹包含那個 commit 才生效。
- **既有模型接軌**：新機制上線時，把每個 ML 任務已安裝的模型登記為平台模型並寫第一筆生效紀錄，只發生一次，不開放給交付包。

### 2.5 退回、解除釘選與下架

- **退回是止損**：把釘選改回同一個 ML 任務下曾經有過生效紀錄的模型版本，不分出處種類，也不限於緊鄰的上一份。退回不經過閘門，但要重新通過可服務檢查。
- **以釘選表達**：退回就是把期望狀態改回舊的 SHA，或 revert 原本的 PR，宣告檔不另加欄位。生效紀錄記下這次生效的依據是退回，並引用該 SHA 先前的生效紀錄。
- **平台模型也能退回**：退回到先前的平台模型時，被釘住的那一份同時重新成為平台模型，之後的重訓和它比。平台模型是哪一份由資料庫紀錄推導，不設指標檔。
- **解除釘選**回到目前的平台模型，不經過閘門，因為待命的平台模型已通過閘門。
- **下架**：只能靠釘選上線的 ML 任務，第一份釘選就出問題時，以同時刪除任務設定與期望狀態檔的方式下架。下架不刪除紀錄與成品；以同一個識別重新上架仍是同一個 ML 任務。

### 2.6 存放與保留

- 成品一律以內容定址存放，交付包與平台模型分開。載入前先比對雜湊。
- **交付包**：曾經生效過的，連同它引用的**凍結資料**永久保留；待定的保留到有判定；從未生效的只能以明確的指令刪除，不做自動清理。
- **平台模型**：保留多份。曾經是現役模型的，不再服務滿 30 天後自動清理；從未服務過的，被取代時立即刪除。生效紀錄不受清理影響。

### 2.7 信任邊界：不載入可執行格式

- **硬規則，平台模型與交付包一體適用**：載入成品的過程不得依檔案內容 import 模組、建構任意型別或呼叫任意 callable。JSON、不允許 pickle 的 `.npz`、LightGBM 原生文字格式與 safetensors 符合；skops、`torch.load` 與 MLflow flavor 不符合。
- **符合定義的新格式不必立 ADR**，隨新任務類型的 PR 進來；要放寬定義才立 ADR。現行允許的格式列在 reference，強制在測試。
- **範圍只到 `src/`**：規則管的是跨進平台存放區的成品。研究空間內部用什麼格式存中間結果不受限制。
- **把成品當成非信任位元組**：載入前先比對目錄雜湊，不一致視為不可服務；第一次解析發生在獨立的 Dagster run，API 只載入已有生效紀錄的 SHA；壓縮格式以解壓後的大小計入上限。不做簽章與沙箱。

### 2.8 主機的部署分支與更新

- **主機追蹤 `origin/main`**，`v*` tag 只是版本標記。改追之前先做一次 `dev` → `main` 發布。
- **止損的短路**：變更全部在期望狀態目錄底下、或只刪除任務設定（下架）的 PR，可以直接進 `main`，之後必須合回 `dev`，由 ruleset 強制。新增或修改任務設定不在例外內。
- **部署專用的 checkout**：資料目錄所在的主要 checkout 只停在 `main`，只由更新指令移動；開發一律在 git worktree 的連結工作樹，正式環境的指令在連結工作樹裡拒絕執行。
- **手動的更新指令**：只改期望狀態時直接 fast-forward，不停服務；其他變更先等執行中的 run 結束，再停服務、更新、重建並執行 smoke check。smoke check 失敗不自動退回。
- **工作樹更新紀錄**：更新指令每次執行都寫一筆 append-only 紀錄，是「主機目前在哪個 commit」的權威來源。生效紀錄的 commit 取自它；已發布預報以發布時刻對回平台版本。
- **雲端與地端的生效時刻不同**：每一版預報檢視網站都要讀得懂上一版匯出端產生的 JSON，由發布 PR 的 CI 驗證。
- **研究出處的規則維持 `origin/dev`**，不要求主機工作樹已經包含它。

### 2.9 監控

- 釘選期間，監控照常評估平台模型，報告標明評估對象，不把它當成現役模型的健康狀態。
- 平台模型已贏過釘選的交付包時，報告要明白顯示。平台重訓連續 3 天沒有勝出，判 `WARNING`。
- 釘選的是平台出處的模型版本時，報告標明這一點、它的訓練截止距今多久，以及待命的平台模型是否已換了一份。

### Rationale & Alternatives Considered

- **取捨一：交付什麼**
  - **選定方案：交付已訓練的成品**。平台不支援訓練的任務類型也能上線；被評估的就是上線的那一份。
  - **候選方案 A：交付配方，由平台重訓**。平台要保有每個任務類型的訓練程式，重訓的結果也不是研究者評估過的那一份。未採納。
  - **候選方案 B：平台重訓以驗證訓練截止與出處**。成本與「交付成品」相違，只能釘選的任務類型也沒有平台訓練程式。未採納，剩餘風險由「研究出處已合併、可供審查」承擔。
- **取捨二：排程重訓與釘選**
  - **選定方案：重訓只更新平台模型，釘選期間照常重訓**。平台模型保持新鮮，解除釘選時可以直接接手。
  - **候選方案 C：訓練全部歸研究者**。改以「平台訓練是選配」表達，不當成全域規則。
  - **候選方案 D：釘選期間略過重訓**。解除釘選時只有過舊的平台模型。未採納。
  - **候選方案 E：重訓結果贏過釘選就自動取代**。現役模型會在沒有人決定的情況下更替，兩者的訓練截止不同，比較也不公平。未採納。
- **取捨三：閘門**
  - **選定方案：有拘束力、由平台以成品重算的相對比較**。契約不依賴默契；核心指標的取捨寫在輸出契約裡，要改就以 PR 修改定義。
  - **候選方案 F：平台重訓不設閘門**。沒有人每天檢查重訓結果。未採納。
  - **候選方案 G：比較只供參考，由人決定**。未採納。
  - **候選方案 H：以監控的絕對門檻擋閘門**。熱浪這類兩個模型一起變差的情況下，擋下新模型留下的會是同樣差而且更舊的模型。未採納。
  - **候選方案 I：採信交付包附上的回測**。研究空間的回測在每個起點重訓，評的是配方，不是交出來的成品。未採納。
  - **候選方案 J：影子部署累積評估資料**。以知悉時間事後回測等效，不必另存影子預測。未採納。
  - **候選方案 K：相同位元組重跑閘門**。等於讓同一份成品反覆換評估窗，直到某次剛好贏。未採納。
  - **候選方案 L：只比共同起點、不看能產出預測的比例**。需要較長歷史的模型在負載有缺口時更常無法預測，這會被藏住。未採納。
- **取捨四：期望狀態與生效**
  - **選定方案：期望狀態在 repo，平台紀錄在資料庫，核對後寫生效紀錄**。人的決定有審查與歷史；判定存在本機資料庫，公開的 CI 連不進去（[ADR-0016](0016-make-repository-public.md)），所以由核對程序強制。
  - **候選方案 M：釘選存在資料庫，以指令寫入**。不經審查，期望狀態也不在 repo。未採納。
  - **候選方案 N：資料目錄的狀態檔**。沒有審查與歷史。未採納。
  - **候選方案 O：MLflow alias**。MLflow 在本專案只寫不讀，ADR-0011 也禁止研究空間寫 registry。未採納。
  - **候選方案 P：維持重啟才生效**。平台模型每天都可能更新，不能靠人重啟。未採納。
  - **候選方案 Q：期望無效就關閉服務**。一個打錯的字就讓預報停發。未採納。
  - **候選方案 R：API 與 Dagster 各自解析期望狀態**。生效時刻會不同。未採納。
- **取捨五：退回與保留**
  - **選定方案：退回免過閘門，資格是曾經生效過；平台模型保留 30 天**。要退回的那一份當初正是被現役模型打敗的，重新比幾乎一定落敗。每日重訓下平台模型幾乎每天換一份，是唯一不經人審就會更替現役模型的路徑，需要不靠研究者的止損。
  - **候選方案 S：退回要重新過閘門**。需要止損時退不回去。未採納。
  - **候選方案 T：宣告檔加上顯式的退回旗標**。退回之後要記得清掉；「曾經生效過」本來就是紀錄裡的事實。未採納。
  - **候選方案 U：容許只能釘選的任務暫時沒有現役模型**。等於把停發做成合法狀態。未採納。
  - **候選方案 V：平台模型只多留前一份**。前一份通常就是昨天那份，問題隔幾天才發現時它多半也有同樣的問題。未採納。
  - **候選方案 W：平台模型永久保留**。每個任務每年累積約 365 份，舊格式也要一直能載入。未採納。
  - **候選方案 X：退回後重訓仍和被退掉的那一份比**。不劣於一份已知有問題的模型，這個門檻沒有意義。未採納。
- **取捨六：信任邊界**
  - **選定方案：沿用不載入可執行格式，寫成精確定義**。既有三個任務類型都不需要放寬。
  - **候選方案 Y：型別白名單載入視為安全**（skops）。信任邊界會變成「白名單有沒有設對」。未採納。
  - **候選方案 Z：子行程沙箱或模型檔簽章**。真實的多人權限隔離不在範圍內；能寫資料目錄的人也能改資料庫，簽章在這個威脅模型下沒有多擋到什麼。未採納。
- **取捨七：主機追哪個分支**
  - **選定方案：追 `origin/main`，止損設短路**。合併進 `dev` 的程式不直接上線；止損的速度不取決於當時 `dev` 上堆了什麼。
  - **候選方案 AA：主機追 `dev`**。未採納。
  - **候選方案 AB：主機追 `v*` tag**。每次換模型或止損都要打 tag，而建立 tag 不經 PR。未採納。
  - **候選方案 AC：另外 clone 一份部署用**。搬移資料目錄有停機風險，錯過的台電快照永久缺失。未採納。
  - **候選方案 AD：smoke check 失敗自動退回**。指令無法判斷這次發布有沒有包含 schema 遷移（[ADR-0017](0017-freeze-baseline-ddl-and-record-schema-migrations.md)）。未採納。

## 3. Consequences

- **正面效益（Positive）**：
  - 研究空間訓練好的模型有正式的上線路徑，平台不支援訓練的任務類型也能服務。
  - 每一次現役模型的更替都有紀錄可查：是哪一份、依據哪一次判定或退回、當時主機在哪個 commit。
  - 換模型不必重啟，API 與 Dagster 不再使用不同的模型。
  - 止損有三條不經過閘門的路：解除釘選、退回、下架。
- **代價與風險（Trade-offs & Risks）**：
  - 新增四張平台紀錄表、一張工作樹更新紀錄表、一個核對程序與一個更新指令；平台模型的存放要搬成內容定址。
  - 交付包以凍結時刻為止的全部資料訓練時，要等 14 天才有判定；訓練時保留最後 14 天不用，才能當下判定。這個取捨由研究者決定。
  - 驗證窗固定 14 天後，高負載預警的正例與異常偵測的校準日都變少，這兩個任務類型的指標穩定度要在實作時確認。
  - 閘門看不出實際值有錯：上游資料錯誤期間，用錯誤資料訓練的候選模型仍可能贏過對手。待命的平台模型換了一份，只是可以考慮解除釘選的訊號。
  - 容忍幅度造成的逐步劣化沒有偵測機制；累積超過 30 天的保留期間，就沒有平台模型可退，只能靠交付包。
  - 推論端要能載入保留期間內每一份成品用到的格式版本；要停止支援某個格式版本，得先刪除用到它的交付包。
  - 解析器本身的漏洞（LightGBM 文字格式、numpy 的 zip 讀取）接受為殘餘風險，以檔案白名單、大小上限與相依升級緩解。
  - 研究者仍能在呼叫寫入函式之前動手腳（例如謊報訓練資料），這由「研究出處已合併、可供審查」承擔。
  - 釘選不會到期，釘選的模型版本會無聲地變舊，只靠監控報告揭露。
  - 可服務檢查與閘門的 run 逾時依賴 Dagster 的 run monitoring，要先開啟。
  - 含 schema 遷移的發布不能把工作樹退回較早的 commit，只能往前修。
- **不做／延後範圍（Out of Scope / Deferred）**：
  - 模型檔簽章與沙箱；真實的多人權限隔離。
  - 主機工作樹的定時拉取（更新指令做成冪等，日後可包一層定時器）。
  - 交付包的自動清理。
  - MLflow 承擔記錄以外的角色。
  - 已發布預報保存當時的輸入。
  - 自動調參的排程化 job、雲端訓練。

## 4. Compliance

- 閘門的單元測試：不劣於與嚴格優於兩種規則、冷啟動改比 naive 基準、評估窗不足判待定、相同 SHA 不重跑、對手已更換的通過判定無效、候選模型能產出預測的起點比例低於對手即落敗。
- 核對程序的單元測試：每一種拒絕理由各有一個情境；期望無效時不寫生效紀錄且舊的現役模型不變；退回免過閘門但重新做可服務檢查；退回平台模型後，平台模型的推導結果是被釘住的那一份。
- 整合測試：寫入新的生效紀錄後，API 不重啟即改用新的模型，回應帶新的 SHA；已發布預報的模型 SHA 與生效紀錄一致。
- 信任邊界的靜態測試：以 AST 限定任務類型的程式只能經允許清單裡的載入呼叫讀檔，並攔下 `src/` 使用 MLflow flavor 的保存與載入。
- 信任邊界的執行期測試：一致性測試在載入模型期間以 audit hook 攔截 pickle，觸發即失敗。正式行程不裝 audit hook。
- 載入的單元測試：目錄雜湊與預期不符時不解析檔案內容；壓縮檔解壓後超過大小上限時在靜態檢查階段拒絕。
- 期望狀態的離線測試：schema、與任務設定一對一、只能釘選的 ML 任務必須有釘選且不得開啟自動訓練。
- `branch-flow` 的測試：head 不是 `dev` 的 PR 只有在變更全部位於期望狀態目錄、或只刪除任務設定時放行。
- smoke check：期望狀態未生效、主要 checkout 不在 `main`、有未提交的變更、HEAD 不等於最新一筆工作樹更新紀錄，任一項成立即失敗。
- 發布 PR 的 CI：以 `main` 上的已發布 JSON fixture 驗證 PR 的預報檢視前端 schema。
- `ops-acceptance`：在主機上以一份交付包走完交付、可服務檢查、評估閘門、釘選、退回，確認 API 不重啟即換模型。
