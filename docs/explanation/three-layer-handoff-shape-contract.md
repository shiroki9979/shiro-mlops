# 模型交付包的三層形狀契約

> - Created: 2026-11-26
> - Last Updated: 2026-11-26
> - Related: [GitHub #279](https://github.com/shiroki9979/shiro-mlops/issues/279)、[GitHub #275](https://github.com/shiroki9979/shiro-mlops/issues/275)、[GitHub #270](https://github.com/shiroki9979/shiro-mlops/issues/270)

本文說明 M11 為模型交付包的輸入輸出形狀訂下的相容性設計：為什麼把形狀拆成三層、各層的邊界在哪裡、哪些變更需要修改 `src/`。這是 M11 的**目標設計，尚未實作**；現行契約仍以 [ML 任務 reference](../reference/ml-tasks.md) 為準。用語依 [GLOSSARY](../../GLOSSARY.md)「6. ML 任務」。

## 1. 要解決的問題

研究者會頻繁交付輸入輸出形狀不同的模型交付包。M11 的成本目標是：新增 ML 任務時若沿用已註冊的任務類型，`src/` 不必改；新增任務類型時，只需要一次有邊界、審過就不必再動的平台端變更。

現行程式把形狀分散在三個地方，而且彼此牽連：

- 任務設定 TOML 的 `[params]` 與 `[weather]` 同時決定訓練配方與 serving 的輸入需求。
- 任務類型的程式裡有會隨研究改變的常數，例如 `direct_classification` 的 `ALERT_PROBABILITY` 與 `MAX_LEAD_HOURS`。
- API 回應型別由任務類型的 `prediction_item` 決定；`WeatherEchoingItem` 會依任務的天氣欄位動態長出欄位，所以研究者改了天氣輸入，回應 schema 也跟著變。

結果是：任一層的小改動都可能牽動下游，或必須改 `src/`。

## 2. 三層與投資順序

形狀分成三層，每一層各有自己的契約：

| 層 | 內容 | 改動頻率 | 契約 |
| :--- | :--- | :--- | :--- |
| 模型內部的特徵 | lag、rolling、日曆、天氣欄位、交互項 | 最常改 | **特徵配方**：交付包內的宣告式配方，詞彙在 `src/` |
| 向平台要的原始輸入 | 序列、天氣欄位、代表點與權重、預報或觀測、lookback | 常改 | **輸入目錄**：平台能供應的原始輸入清單，在 `src/` |
| 交給下游的輸出 | API 回應、已發布預報、預報實績、預報檢視 | 偶爾才改 | **輸出契約**：具名的產出 schema，在 `src/` |

投資的優先順序依改動頻率排列：特徵配方 > 輸入目錄 > 輸出契約。改得越頻繁的層，越要確保改動落在「重新交付即可」的範圍內。

三層彼此隔離，一層的改動不會滲到下一層：

- 配方改了，推論端從現役模型的宣告重新推出 lookback、`history_coverage` 與天氣種類，任務設定與預測輸入關卡都不必改。
- 輸入改了，回應 schema 不變，因為天氣回聲改成固定形狀的 `inputs` 物件（見[第 6 節](#6-輸出契約)）。

## 3. 共同原則：名稱即契約，只增不改

三層都採同一個版本化原則：

- 每一種特徵、每一個輸入目錄項目、每一個輸出契約都有固定的名稱。名稱一旦被已驗收的交付包使用，它的語意就不再改變。
- 要改語意就用新名稱。例如發現 `rolling_std` 的計算有誤，就新增 `rolling_std_v2`；舊名繼續以原本的語意服務引用它的交付包。
- 只有在平台存放的交付包都不再引用某個名稱時，才可以移除它。
- 三層都不設整體版本號。宣告檔本身的結構另有一個 `format_version`（見[第 7 節](#7-宣告格式版本的支援期)）。

這樣推論端只需要保證一件事：平台存放的交付包所引用的每個名稱都還在。整體版本號（例如「特徵詞彙 v3」）則會讓平台同時保有每一版的完整實作，即使大部分項目在版本之間從未改變。

## 4. 特徵配方

- **詞彙只有一份**，放在 `src/shiro_mlops/features/`，`lab/` 的訓練與 serving 都呼叫同一份程式。
- **任務類型宣告自己能解譯哪些特徵種類**。例如遞迴回歸只能使用可以從預測值逐步重算的負載衍生特徵。配方引用了任務類型不支援的種類，驗收時拒絕。
- **配方只含特徵種類與其參數**，例如 `lags=[1,2,24,336]`、rolling 視窗、`day_off`、天氣欄位。估計器的超參數不屬於配方，留在模型檔裡，平台不比對。
- **任務類型參數另成一節**：屬於任務類型語意的參數，例如高負載門檻的 `window_days` 與 `quantile`、預警機率門檻、最大提前時數、重建視窗長度、異常門檻分位數，寫在宣告的「任務類型參數」一節，schema 由任務類型定義，不算特徵配方。

配方內容在詞彙範圍內的改動，重新交付即可。需要新的特徵種類時，對 `src/` 的詞彙做一次有邊界的擴充：新增種類的實作，並讓解譯它的任務類型通過共用的一致性測試。

## 5. 輸入目錄

輸入目錄是 `src/` 裡的一份明確清單，同步記錄在 reference，列出宣告可以引用的原始輸入：

- **序列**：目前只有 `hourly_actual_load` × `nationwide`。
- **天氣欄位**：只列出整條 serving 路徑都已存在的欄位，也就是預報、預報版本回退與降級都能處理。目前只有溫度與相對濕度。
- **代表點**：氣象資料實際擷取的地點（`CWA_LOCATION_ALLOWLIST`）。
- **天氣模式**：預報或觀測。
- **日曆**：台灣假日。

**有入庫不等於在目錄裡。** 氣象署的 7 個預報欄位都已入庫，但以測站觀測替代的降級只接上了溫度與相對濕度。露點、體感溫度與降雨機率在測站觀測裡沒有對應欄位；風速與風向有觀測欄位，但還沒接上降級。這些欄位在 serving 時一旦缺值就無法維持服務，所以不列入目錄。

**代表點、權重與天氣欄位由交付包的宣告提供。** 預測對象（`subject`、`target`）仍是 ML 任務的身分，留在任務設定；任務設定的 `[weather]` 降為只用於平台訓練，地位和 `[params]` 相同。研究者改用已入庫地點的加權組合時，重新交付即可。

**目錄以外的項目驗收時拒絕。** 把已入庫的資料補進目錄（例如替風速接上觀測降級）是一次 `src/` PR。全新資料來源的擷取不在本設計範圍內。

## 6. 輸出契約

### 6.1 契約是什麼、誰綁誰

- 輸出契約是 `src/` 裡的具名 schema。現有三個：負載曲線（`predicted_load_mw`）、高負載預警（`is_high_load`、`probability`、`threshold_mw`）與異常旗標（`anomaly_score`、`is_anomaly`、`threshold`）。
- 任務設定指名 ML 任務的輸出契約；交付包的宣告指名自己產出的契約；驗收時兩者必須相同。ML 任務綁的是輸出契約，不是某個任務類型。
- 任務類型宣告自己能產出哪些契約，取代現行的 `prediction_item`。API 的回應型別由輸出契約建立。
- **輸出契約包含 ML 任務承諾的時程範圍**。交付包宣告自己支援的最大時程，比承諾的範圍短就驗收拒絕；否則原本合法的請求（例如 `horizon_hours=100`）會在釘選後失敗。
- 天氣回聲移出契約的固定欄位，改成固定形狀的 `inputs` 物件（欄位 → 代表點 → 值與來源，併入現行的 `weather_sources`）。

### 6.2 相容擴充與破壞性變更

| 類別 | 例子 | 走法 |
| :--- | :--- | :--- |
| 相容擴充 | 新增選填欄位，例如 `predicted_load_mw_p10`、`predicted_load_mw_p90` | 先以 `src/` PR 把欄位加進契約，交付包才能產出 |
| 破壞性變更 | 刪除或改名欄位；改變單位或語意；改變時間粒度；改變預測對象；縮短時程範圍 | 新的輸出契約名稱，以及新的 ML 任務 |

輸出契約沒有主版本號，同一個 ML 任務不會中途更換契約。輸出契約是 ML 任務身分的一部分，破壞性變更等於另一個 ML 問題，所以開新的 ML 任務（新的 `task_id`）。

### 6.3 新舊並行與退場

- 新舊 ML 任務各有自己的 `/tasks/{task_id}/predict` 端點與現役模型，可以同時運行。
- 舊任務退場時，刪除它的任務設定即可，不設強制過渡期，由平台維護者在 PR 中決定。它的已發布預報與預報實績照原樣保存，不刪除。

### 6.4 擴充欄位的產出與保存

- 交付包產出契約裡沒有的欄位，驗收時拒絕。
- 現役模型沒有產出某個選填欄位時，API 回應中的該欄位為 `null`。例如解除釘選後回到平台模型，而平台模型不產出 P10。
- 下游只保存自己認得的欄位。`issued_forecast_step` 只存 `predicted_load_mw`；要保存 P10 與 P90，需要依 [ADR-0017](../adr/0017-freeze-baseline-ddl-and-record-schema-migrations.md) 做 schema 遷移，並修改預報實績與預報檢視。擴充欄位先出現在 API，下游是否跟進另外決定。

### 6.5 下游的歸屬

已發布預報、預報實績與預報檢視在 M11 仍綁定動態視界預報，M11 不改它們的 schema。規則是：下游依輸出契約定義，ML 任務在任務設定中選擇加入。等到第二個需要下游的 ML 任務出現時，才一般化，例如替 `issued_forecast` 加上 `task_id`。釘選的交付包只要產出負載曲線契約，就照常進入現有下游。預報檢視是公開介面，要呈現哪個 ML 任務屬於產品決定。

## 7. 宣告格式版本的支援期

- 推論端必須能載入平台存放的交付包所用到的每一個 `format_version`。
- 每個曾被接受的 `format_version`，都在 `tests/fixtures/` 放一份黃金交付包，由一致性測試逐一載入並預測。
- 要讓某個 `format_version` 退場，必須先確認平台存放的交付包都不再使用它，之後才能刪除它的 fixture 與讀取程式。
- 平台模型每天重訓，不享有舊格式的支援，格式改變後重訓一次即可。

支援範圍刻意限定為「平台存放的」交付包，而不是「所有曾經驗收的」交付包，以免承諾一個沒有上限的支援期。平台要保留多少份交付包，另案決定。

## 8. 情境對照

| 情境 | 層 | 要改 `src/` 嗎 | 走法 |
| :--- | :--- | :--- | :--- |
| lag 改成 336、rolling 改成 72 | 特徵配方 | 否 | 重新交付 |
| 加入溫度 × 小時的交互項 | 特徵配方 | 是，一次 | 擴充特徵詞彙 |
| 修正 `rolling_std` 的計算 | 特徵配方 | 是，一次 | 新增 `rolling_std_v2`，舊名保留 |
| 台北 0.5、台中 0.3、高雄 0.2 加權 | 輸入目錄 | 否 | 三點都已入庫，重新交付 |
| 使用風速 | 輸入目錄 | 是，一次 | 接上觀測降級後列入目錄 |
| 使用降雨機率 | 輸入目錄 | 是 | 測站觀測沒有對應欄位，要先定義它的降級方式 |
| 使用尚未入庫的資料來源 | 輸入目錄 | 是 | 先擷取入庫，不在本設計範圍 |
| 加上 P10 與 P90 | 輸出契約（相容擴充） | 是，一次 | 契約加選填欄位；下游保存需另做遷移 |
| 只能預測 48 小時的模型 | 輸出契約 | — | 驗收拒絕；改開新的 ML 任務 |
| 15 分鐘粒度的負載曲線 | 輸出契約（破壞性） | 是 | 新契約與新的 ML 任務 |
| 估計器換成 XGBoost | 不屬於三層 | 是，一次 | 新的任務類型 |

表中「開新的 ML 任務」需要新增一份任務設定。任務設定目前放在 `src/` 內，是否搬出另案決定（[GitHub #388](https://github.com/shiroki9979/shiro-mlops/issues/388)）。

## 9. 被否決的做法

- **每一層設一個整體版本號**：平台必須保有每一版的完整實作，而大部分項目在版本之間從未改變。
- **同一個 ML 任務內升級輸出契約的主版本**：API 消費者、已發布預報與預報實績會在同一個 `task_id` 下混雜兩種形狀；預報實績的誤差也會失去可比性。
- **依任務的天氣欄位動態產生回聲欄位**：輸入層的改動會變成輸出層的破壞性變更。
- **有入庫就列入輸入目錄**：缺少降級路徑的欄位一旦缺值，就無法維持預報服務。
- **允許時程範圍較短的交付包釘選**：原本合法的請求會在釘選後失敗。
- **M11 就把下游一般化到所有輸出契約**：目前只有動態視界預報需要下游，一般化沒有第二個實例可以驗證。
- **代表點留在任務設定，作為 ML 任務的身分**：研究者每改一次代表點或權重，就要改任務設定。
- **承諾載入所有曾經驗收的交付包**：支援期會沒有上限，舊格式的讀取程式永遠無法退場。
