# Classic software-engineering views and empirical findings on code comments, compared with the proposed agent-era comment rule

The rule under comparison, in short: (a) names, types, small functions and tests carry purpose and behaviour, so comments that only restate them are deleted; (b) only two kinds of comment are allowed: a 1–3 line module/class header stating role and invariants ("天條"), and "why-not" comments beside deliberate but odd-looking code; (c) why-not comments must name the code they protect and are deleted with it; (d) runtime-behaviour descriptions follow the same rules. The author's reasoning is that agents read code tirelessly, so knowledge no longer needs to be duplicated across design docs, headers, inline comments and commit messages.

Method note: this session's network allowed only some hosts. Primary texts were read in full for the Ousterhout–Martin debate (GitHub), the Google Python style guide, PEP 8, PEP 257, Go Doc Comments, the Linux kernel coding style, the Linux kernel Rust coding guidelines, the clippy lint source and Sphinx autodoc. Papers hosted at usi.ch, tudelft.nl and stanford.edu, and *.github.io pages, could not be fetched, so those findings rest on abstracts, bibliographic records and search-result summaries, and are marked as such.

## Q1. Clean Code ch. 4 (Robert C. Martin): which categories match "header invariants" and "why-not", and what does Clean Code allow that the rule forbids?

### Takeaway
The rule is close to *Clean Code*'s philosophy ("explain yourself in code", "comments are always failures") and shares most of its "bad comments" list. It is stricter than *Clean Code* in one respect: *Clean Code*'s eight "good comment" categories include Legal, Informative, Clarification, TODO and Javadocs in Public APIs, and the rule has no slot for any of them. Only Explanation of Intent, Warning of Consequences and Amplification map cleanly onto "why-not" (and partly onto header invariants).

### Cited Findings
- Martin's core stance, as quoted by Ousterhout ("page 54"): "The proper use of comments is to compensate for our failure to express ourselves in code. Note that I use the word failure. I meant it. Comments are always failures. We must have them because we cannot always figure out how to express ourselves without them... Every time you write a comment, you should grimace and feel the failure of your ability of expression." — [aposd-vs-clean-code README](https://github.com/johnousterhout/aposd-vs-clean-code)
- The chapter opens: "Nothing can be quite so helpful as a well-placed comment. Nothing can clutter up a module more than frivolous dogmatic comments. Nothing can be quite so damaging as an old comment that propagates lies and misinformation." It also says: "the only truly good comment is the comment you found a way not to write." — [Clean-Code-Notes (community chapter notes, quoting the book)](https://github.com/JuanCrg90/Clean-Code-Notes); Ousterhout quotes the second line as well in [aposd-vs-clean-code](https://github.com/johnousterhout/aposd-vs-clean-code)
- Ousterhout's count: "Chapter 4 spends 4 pages talking about good comments, followed by 15 pages talking about bad comments." Martin's reply: "The difference in page count is because there are just a few ways to write good comments, and so many more ways to write bad ones." — [aposd-vs-clean-code](https://github.com/johnousterhout/aposd-vs-clean-code)
- **Good comments** (subsection headings of ch. 4): Legal Comments, Informative Comments, Explanation of Intent, Clarification, Warning of Consequences, TODO Comments, Amplification, Javadocs in Public APIs. The Pearson sample PDF's table of contents confirms these headings. — [Clean-Code-Notes](https://github.com/JuanCrg90/Clean-Code-Notes); [Pearson sample/TOC](https://ptgmedia.pearsoncmg.com/images/9780135398579/samplepages/9780135398579_Sample.pdf) (via search summary)
  - Legal: "copyright and authorship statements are necessary and reasonable things to put into a comment at the start of each source file."
  - Informative: useful, "but it is better to use the name of the function to convey the information where possible", for example renaming to `responderBeingTested`. (This is the rule's "names over comments".)
  - Explanation of Intent: "provides the intent behind a decision."
  - Clarification: allowed "when its part of the standard library, or in code that you cannot alter".
  - Warning of Consequences: "warn other programmers about certain consequences."
  - TODO: "explains why the function has a degenerate implementation and what that function's future should be."
  - Amplification: "amplify the importance of something that may otherwise seem inconsequential."
  - Javadocs in Public APIs: "There is nothing quite so helpful and satisfying as a well-described public API... It would be difficult, at best, to write Java programs without them." — all from [Clean-Code-Notes](https://github.com/JuanCrg90/Clean-Code-Notes)
- **Bad comments** ("Most comments fall into this category"): Mumbling, Redundant Comments, Misleading Comments, Mandated Comments ("It is just plain silly to have a rule that says that every function must have a javadoc, or every variable must have a comment"), Journal Comments ("Today we have source code control systems"), Noise Comments, Don't Use a Comment When You Can Use a Function or a Variable, Position Markers, Closing Brace Comments, Attributions and Bylines, Commented-Out Code, HTML Comments, Nonlocal Information ("make sure it describes the code it appears near"), Too Much Information ("Don't put interesting historical discussions... into your comments"), Inobvious Connection ("The connection between a comment and the code it describes should be obvious"), Function Headers ("A well-chosen name for a small function that does one thing is usually better than a comment header"), Javadocs in Nonpublic Code. — [Clean-Code-Notes](https://github.com/JuanCrg90/Clean-Code-Notes)
- In the debate, Martin says "I'm not hostile to comments in general. I _am_ very hostile to gratuitous comments." He also gives the historical motive: in the '70s and '80s comments were necessary for assembly and FORTRAN, "it became conventional wisdom to write comments by default... In _Clean Code_ I decided to fight that mindset." — [aposd-vs-clean-code](https://github.com/johnousterhout/aposd-vs-clean-code)
- Martin on verifiability: "I look at every comment as potential misinformation. At best they are a way to crosscheck the author's intent against the code... the best comments tell me something surprising and verifiable about the code. The worst are those that waste my time telling me something obvious, or incorrect." — [aposd-vs-clean-code](https://github.com/johnousterhout/aposd-vs-clean-code)
- Martin on javadoc: "I'm not opposed to Javadocs as a rule; but I write them only when absolutely necessary. I also have an aversion for descriptions and `@param` statements that are perfectly obvious from the method signature." — [aposd-vs-clean-code](https://github.com/johnousterhout/aposd-vs-clean-code)

### Inferences
- How the categories map onto the rule:
  - **why-not ≈** Explanation of Intent + Warning of Consequences + Amplification. The rule narrows these to code that "looks unreasonable/redundant/arbitrary". *Clean Code*'s intent comments are broader and do not require the code to look odd.
  - **Header invariants ≈** partly Warning of Consequences at module scope, and partly the class-level part of "Javadocs in Public APIs". *Clean Code* has no "module invariant" category as such.
  - **Forbidden by the rule but allowed by Clean Code:** Legal, Informative, Clarification (wrapping code you cannot alter), TODO, and method-level public-API Javadoc. Strictly applied, the rule even forbids license/SPDX headers.
- The rule's requirement that a why-not comment "name the code it protects so it can be re-validated" puts into practice Martin's "surprising and verifiable" criterion and *Clean Code*'s "Inobvious Connection" anti-pattern.
- The rule's deduplication argument ("knowledge no longer needs to be repeated across design doc, headers, inline comments and commit messages") mirrors *Clean Code*'s "Journal Comments" and "Nonlocal Information/Too Much Information" items. *Clean Code* argued the same thing in 2008, with version control as the enabling technology.
- Historical parallel: Martin's 2008 reasoning ("comments were necessary for assembly/FORTRAN; modern languages reduce the need") has the same shape as the agent-era argument ("agents read code tirelessly, so comments are needed less"). Ousterhout's rebuttal of the first ("I don't agree that comments are less necessary today than they were 40 years ago") is the natural template for a rebuttal of the second.
- Conflict with this repository: `/home/user/shiro-mlops/AGENTS.md` prescribes code markers of the form `TODO(#123)` for tech debt. *Clean Code* allows TODO comments; the rule as written does not. The rule would need an explicit exemption for issue-linked TODO markers.

### Gaps
- I could not verify page numbers for individual subsections, other than Ousterhout's citation of "page 54" for the "failures" passage. The category texts come from community notes that quote the book; I did not read the book itself.

## Q2. Ousterhout, *A Philosophy of Software Design* (1st/2nd ed.) and the 2024–25 Ousterhout–Martin debate: does "interface comments define abstractions" conflict with deleting docstrings that "repeat signatures"?

### Takeaway
Ousterhout agrees with the rule that comments must not repeat the code, and his comments-summary agreement with Martin ("implementation code only needs comments when the code is nonobvious") matches the rule's restraint on inline comments. He firmly disagrees with the rule's implicit ban on method-level interface comments. In his view a signature is "pretty rare[ly]" a complete interface, tests are "a poor form of documentation", and "it is not possible to define interfaces and create abstractions without a lot of comments." Deleting docstrings that only restate the signature is fine by him. Deleting the semantic content that docstrings usually carry (formats, ordering, duplicate handling, side effects, preconditions) is not, unless the class header absorbs it.

### Cited Findings
- The debate was conducted "between September 2024 and February 2025" (per the README's framing, as summarized by fetch) and covers three topics: method length, comments, and TDD. — [aposd-vs-clean-code](https://github.com/johnousterhout/aposd-vs-clean-code)
- Ousterhout: "Comments are crucially important and add enormous value to software. The problem is that there is a lot of important information that simply cannot be expressed in code." — [aposd-vs-clean-code](https://github.com/johnousterhout/aposd-vs-clean-code)
- Two reasons for comments. (1) Abstraction: "Simply put, without comments there is no way to have abstraction or modularity... It should be possible to use a method without reading its code. The way we achieve this is by writing a header comment that describes the method's *interface* (all the information someone needs in order to invoke the method)." (2) "important information that is not obvious from the code." — [aposd-vs-clean-code](https://github.com/johnousterhout/aposd-vs-clean-code)
- On `addSongToLibrary(String title, String[] authors, int durationInSeconds)`, Ousterhout lists what the signature omits: author-string format, whether author order matters, behaviour on a duplicate title, and storage. He then says: "Sometimes the signature of a method... contains all the information needed to use it, but this is pretty rare." — [aposd-vs-clean-code](https://github.com/johnousterhout/aposd-vs-clean-code)
- Martin's counter-position, which is close to the rule: "there are times when the signature of a method is an incomplete abstraction and a comment is required. This is especially true when the interface is part of a public API... Within a single development team, however, long descriptive comments on interfaces are often more of an impediment than a help. The team has intimate knowledge of the internals... and will generally be able to understand an interface simply from its signature." — [aposd-vs-clean-code](https://github.com/johnousterhout/aposd-vs-clean-code)
- Ousterhout's rebuttal: "I find that I quickly forget code that I wrote just a few weeks ago. In a project of any size, I think your approach would result in developers spending large amounts of time reading code to re-derive the interfaces, and probably making mistakes along the way." — [aposd-vs-clean-code](https://github.com/johnousterhout/aposd-vs-clean-code)
- On redundancy between a name and a comment: Martin says "The first sentence is redundant with the name `isMultipleOfNthPrimeFactor` and so could be deleted. The warning of the side effect is useful." Ousterhout replies: "You propose to eliminate the redundancy between the comment and the method name by dropping the comment; I would eliminate the redundancy by shortening the method name... in this case the comment is *more* precise (the method name can't include text like `primes[n]`)." Martin concedes: "There are times when precision is better expressed in a comment." — [aposd-vs-clean-code](https://github.com/johnousterhout/aposd-vs-clean-code)
- On precision versus English: Martin says "Human languages are imprecise and full of ambiguities." Ousterhout replies that "comments typically don't need the same degree of precision as code. Comments often contain qualitative information such as *why* something is being done, or the overall idea of something." Martin: "I have no argument with that statement." — [aposd-vs-clean-code](https://github.com/johnousterhout/aposd-vs-clean-code)
- On tests as documentation: Ousterhout says "unit tests are a poor form of documentation. Comments are a much more effective form of documentation, and you can put them right next to the relevant code." Martin replies: "Nowadays it's very easy to find the tests for a function by using the 'where-used' feature of the IDE. As for comments being better, if that were true then no one would publish example code." — [aposd-vs-clean-code](https://github.com/johnousterhout/aposd-vs-clean-code)
- Ousterhout's summary of the comments section (Martin: "This is a fair assessment"):
  - "I would probably write 5-10x more lines of comments for a given piece of code than you would."
  - "I believe that missing comments are a much greater cause of lost productivity than erroneous or unhelpful comments; you believe that comments are a net negative, as generally practiced."
  - "I believe that it is not possible to define interfaces and create abstractions without a lot of comments. You agree for public APIs, but see little need to comment interfaces that are internal to the team."
  - "We agree that implementation code only needs comments when the code is nonobvious."
  - "Overall, we struggled to find areas of agreement on this topic."
  — [aposd-vs-clean-code](https://github.com/johnousterhout/aposd-vs-clean-code)
- Ousterhout's own practice: "Most methods I write have no comments in the body, just a header comment describing the interface. But this code is subtle and tricky, so it needs a lot of comments." — [aposd-vs-clean-code](https://github.com/johnousterhout/aposd-vs-clean-code)
- APOSD Chapter 13 is titled "Comments Should Describe Things that Aren't Obvious from the Code". His CS190 lecture notes say "obvious" is judged "from the perspective of someone reading your code for the first time (not you)" and warn "do not describe the implementation in the interface documentation!" — [Ch. 13 mirror](https://lamb.github.io/a-philosophy-of-software-design/comments-should-describe-things-that-are-not-obvious-from-the-code.html) (title only, via search); [Ousterhout CS190 lecture "Writing Comments"](https://web.stanford.edu/~ouster/cgi-bin/cs190-winter18/lecture.php?topic=comments) (via search snippet; page not fetchable here)
- The 2nd edition (July 2021) has "only a few significant changes". Ousterhout added subsections in two chapters comparing APOSD with *Clean Code*, noting "significant differences of opinion on topics such as the length of methods and the role of comments". — [Ousterhout book page](https://web.stanford.edu/~ouster/cgi-bin/book.php) (via search summary)

### Inferences
- The two parts of the rule fall on different sides of this debate.
  - "Delete docstrings repeating signatures" is consistent with both authors. Ousterhout would shorten the name or enrich the comment; he would not keep a pure restatement.
  - The ban on method-level interface comments (only module/class headers are allowed) sides with Martin's "within a team, signatures suffice" position. Ousterhout says that position "abdicates" abstraction.
- The rule's agent-era premise ("agents read code tirelessly") is close to a restatement of Martin's "the team keeps the code loaded" argument. Ousterhout's objection still applies, and arguably more strongly. Agents have no persistent memory across sessions, so each session is a first-time reader and must "re-derive the interfaces... probably making mistakes along the way." Cheap reading lowers the time cost of re-deriving; it does not lower the error risk.
- To be compatible with Ousterhout, the rule could permit a narrow third category: interface semantics not expressible in names/types (units, formats, ordering, idempotency, duplicate handling, side effects, preconditions). Alternatively, it could treat these explicitly as "header invariants" at function scope. The rule as written does neither, so this information either moves into tests (which Ousterhout calls "a poor form of documentation") or is lost.
- Ousterhout's "Comments augment the code by providing information at a different level of detail" framing (higher-level intuition and lower-level precision, ch. 13 sections) suggests that the rule's 1–3 line header captures the higher-level intuition. Nothing in the rule captures lower-level precision, such as inclusive/exclusive ranges, beyond what types allow.

### Gaps
- I could not fetch the APOSD chapter 13 text, so I cannot quote "Lower-level comments add precision / Higher-level comments enhance intuition", "comments first" (ch. 15 in the 1st ed.), or "cross-module design decisions" verbatim. Whether the 2nd edition changed the "write comments first" guidance could not be confirmed; a third-party summary using that phrase was judged unreliable.

## Q3. McConnell (*Code Complete*), Kernighan & Pike (*The Practice of Programming*), Knuth (literate programming), Atwood, and Chesterton's fence

### Takeaway
The mainstream tradition agrees with the rule on what to delete: comments that repeat the code are useless, and comments should explain *why* or *intent*, not *how*. It is broader than the rule on what to keep: McConnell's summary and intent comments, and Kernighan & Pike's "comment functions and global data". Knuth's literate programming is the opposite pole. Chesterton's fence is the standard rationale for why-not comments, and the rule's why-not category is effectively a sign posted on the fence.

### Cited Findings
- McConnell (*Code Complete* 2nd ed., ch. 32 key points): comments "should say things about the code that the code can't say about itself—at the summary level or the intent level." In the chapter's dialogue, good comments do not repeat or explain the code; they "clarify its intent" and explain "at a higher level of abstraction than the code, what you're trying to do". — [O'Reilly CC2 Key Points](https://www.oreilly.com/library/view/code-complete-2nd/0735619670/ch32s08.html); [O'Reilly "To Comment or Not to Comment"](https://www.oreilly.com/library/view/code-complete-2nd/0735619670/ch32s03.html) (via search summary)
- McConnell's "Kinds of Comments", per course slides that follow the book: "Repeat of the Code" (useless), explanation, marker, summary, and "Description of the code's intent", which is called best "since it explains the why, not the how". — [TAMU commenting slides](https://people.engr.tamu.edu/choe/choe/courses/13fall/315/lectures/commenting.pdf); [SDSU notes following CC ch. 19 (1st ed.)](https://eli.sdsu.edu/courses/fall95/cs596_1/notes/comments/Comments.html) (via search summary)
- Kernighan & Pike's comment guidelines (as listed in lecture slides): "Don't belabour the obvious", "Comment functions and global data", "Don't contradict the code", "Don't comment bad code, rewrite it", "Clarify, don't confuse". The Stack Overflow Blog attributes "Don't comment bad code—rewrite it" to Kernighan & Plauger's earlier *The Elements of Programming Style*. — [TXState slide on Kernighan/Pike](https://userweb.cs.txstate.edu/~hn12/teaching/2041/lec/G/slide012.html); [Stack Overflow Blog 2021](https://stackoverflow.blog/2021/07/05/best-practices-for-writing-code-comments/) (via search summary)
- Rob Pike, *Notes on Programming in C*: avoid big comment blocks except before vital sections such as the central data-structure declaration, and "comments on data are usually much more helpful than on algorithms". — [Pike, Notes on Programming in C](https://www.cs.princeton.edu/courses/archive/spr01/cs217/pike.html) (via search summary)
- Knuth, "Literate Programming" (*The Computer Journal* 27(2):97–111, 1984): "let us concentrate rather on explaining to human beings what we want a computer to do." — [Knuth 1984 reprint](https://www.cs.tufts.edu/~nr/cs257/archive/don-knuth/web.pdf) (wording confirmed via search summary)
- Jeff Atwood, "Code Tells You How, Comments Tell You Why" (Coding Horror, Dec 2006): the best kind of comments are the ones you don't need; code tells you how the program works, comments can tell you why. His 2008 post "Coding Without Comments" argues that junior developers lean on comments "to tell the story" when the code should. — [Atwood 2006](https://blog.codinghorror.com/code-tells-you-how-comments-tell-you-why/); [Atwood 2008](https://blog.codinghorror.com/coding-without-comments/) (via search summary)
- Chesterton's fence in software: "change should not be made until the reasoning behind the current state of affairs is understood" (thoughtbot). Atomic Object uses it to justify comments as signposts for future developers. Critics note that the underlying assumption is weakening, since some code has no original rationale to recover ("Chesterton's gap"). — [thoughtbot](https://thoughtbot.com/blog/chestertons-fence); [Atomic Object](https://spin.atomicobject.com/chestertons-fence-code-comments/); [Tulkens, "From Chesterton's fence to Chesterton's gap"](https://stephantul.github.io/blog/unfence/) (via search summary)

### Inferences
- The rule's why-not category is Chesterton's fence turned into a convention. It is also the category most valuable to agents, which tend to "clean up" apparently redundant code. A fence without a sign is likely to be removed by a tireless reader that cannot tell deliberate from accidental.
- The rule forbids McConnell's "summary" comments (for example, a one-line summary above a block) unless the block is extracted into a named function. This follows Martin's "Don't use a comment when you can use a function", not McConnell.
- Kernighan & Pike's "Comment functions and global data" and Pike's "comments on data are usually much more helpful than on algorithms" conflict with the rule's ban on "field comments" in cases where a field has units, sentinel values or ranges that its name does not carry. The rule only bans field comments that repeat the field name, but in practice the line is subjective.
- Knuth's position shows that the rule sits at the minimal end of a spectrum that runs from "code as literature" to "code as its own documentation".

### Gaps
- I could not verify McConnell's full list of comment kinds, including whether a sixth kind, "information that cannot possibly be expressed by the code itself", is in the book. My recollection is that it is, but it is unverified. *The Practice of Programming* section/page numbers are also unverified.

## Q4. Design by Contract, class invariants and executable checks versus prose "天條"; Rust `// SAFETY:` and clippy as an analogue

### Takeaway
Prose invariants are unchecked claims. The tradition from Meyer's Design by Contract onward, and today's tooling, prefer invariants that are executable or at least mechanically linked to the code. Rust's `# Safety` / `// SAFETY:` convention, enforced by clippy, is the closest existing analogue to the rule. It mandates a justification comment at a specific code site, mechanically forbids the comment when the justified construct is absent, and separates the contract (doc) from the local justification (comment). Even so, the lint checks that the comment exists, not that it is true.

### Cited Findings
- clippy `undocumented_unsafe_blocks` (category **restriction**, so opt-in and not on by default; added in 1.58.0): "Checks for `unsafe` blocks and impls without a `// SAFETY: ` comment explaining why the unsafe operations performed inside the block are safe. Note the comment must appear on the line(s) preceding the unsafe block with nothing appearing in between." Rationale: "Undocumented unsafe blocks and impls can make it difficult to read and maintain code. Writing out the safety justification may help in discovering unsoundness or bugs." Config: `accept_comment_above_statement`, `accept_comment_above_attributes`. — [clippy source](https://github.com/rust-lang/rust-clippy/blob/master/clippy_lints/src/undocumented_unsafe_blocks.rs)
- clippy `unnecessary_safety_comment` (restriction, 1.67.0): "Checks for `// SAFETY: ` comments on safe code." The reason given: "Safe code has no safety requirements, so there is no need to describe safety invariants." — [clippy source](https://github.com/rust-lang/rust-clippy/blob/master/clippy_lints/src/undocumented_unsafe_blocks.rs)
- Linux kernel Rust guidelines: "`// SAFETY:` comments... must appear before every `unsafe` block, and they explain why the code inside the block is correct/sound". "`# Safety` sections specify the contract that callers (for functions) or implementors (for traits) need to abide by. `// SAFETY:` comments show why a call... actually respects the preconditions stated in a `# Safety` section." On trivial cases: "While sometimes the reason might look trivial and therefore unneeded, writing these comments is not just a good way of documenting what has been taken into account, but most importantly, it provides a way to know that there are no *extra* implicit constraints." The guidelines also note "Conventions on comments and documentation are not checked by" tooling (truncated in source view), and that "Comments should not be used for documentation purposes: comments are intended for implementation details, not users." — [kernel Documentation/rust/coding-guidelines.rst](https://github.com/torvalds/linux/blob/master/Documentation/rust/coding-guidelines.rst)
- Python DbC: icontract provides `require`/`ensure` and an `invariant` class decorator. Per its docs, an invariant "should hold after initialization and before and after a call to any public instance method". A companion `sphinx-icontract` exists for rendering contracts in docs. — [icontract on PyPI](https://pypi.org/project/icontract/) (via search summary)

### Inferences
- The rule's "why-not comments must name the code they protect and be deleted with it" matches the pair `undocumented_unsafe_blocks` + `unnecessary_safety_comment` almost exactly: required adjacency on one side, forced removal when the protected construct disappears on the other. Rust has a compiler-visible anchor (`unsafe`); arbitrary "odd-looking code" has none. The rule's "name the protected code" clause is a manual substitute for that anchor, so a linter cannot enforce it without some marker convention (for example, a tag such as `# WHY-NOT(<symbol>)`).
- The Rust split between `# Safety` (contract, for callers) and `// SAFETY:` (justification, at the site) maps onto the rule's "header invariants" (contract) and "why-not" (local justification). Rust places contracts at **function** level as well as type level, whereas the rule allows them only at module/class level.
- Calling a prose invariant "天條" (an inviolable rule) raises its authority without raising its verifiability. Martin's "potential misinformation" critique and PEP 8's "contradict the code" warning (Q6) apply with full force. The Design-by-Contract tradition suggests pairing each header invariant with an executable guard: type, assertion, validator, or a named test that the header cites. That way violations surface as failures, not as reader judgement. In this repo, pydantic validators, typed config schemas and pytest tests are the obvious carriers. (This is inference; I did not fetch pydantic or Meyer sources.)
- The kernel's remark that even trivial-looking SAFETY comments show "there are no *extra* implicit constraints" is an argument against the rule's minimalism. Writing the justification also documents the *absence* of further constraints, which an agent cannot infer from silence.

### Gaps
- I did not fetch Bertrand Meyer's primary texts (*Object-Oriented Software Construction*, Eiffel docs) for exact definitions of class invariants. The `deal` library, the pydantic validator docs, and clippy's `missing_safety_doc` lint (from memory, in the default-on style group) were not verified in this session.

## Q5. Architecture Decision Records: division of labour with commit messages and comments; single source of truth versus locality

### Takeaway
ADRs (Nygard 2011) are the canonical home for architecture-level "why", including rejected alternatives and consequences. They are immutable and superseded rather than edited, which makes them historical records, not current specifications. This supports the rule's de-duplication: design rationale need not be repeated in file headers. It also means ADRs cannot replace local why-not comments, because the reader at a code site does not see them. The rule's two allowed categories map well onto "what must be visible at the point of change", while ADRs and commit messages keep the history.

### Cited Findings
- Nygard's format consists of Title, Context, Decision, Status and Consequences. Consequences describe "the resulting context, after applying the decision. All consequences should be listed here, not just the 'positive' ones." Status is "proposed" or "accepted", and later decisions may mark earlier ones "deprecated" or "superseded" with a reference. — [Nygard, "Documenting Architecture Decisions" (Cognitect, 2011-11-15)](https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions) (via search summary); [Red Hat on ADRs](https://www.redhat.com/architect/architecture-decision-records)
- Fowler: Nygard coined "Architecture Decision Record" in a 2011 ADR-formatted article. ADRs should not be modified when a decision changes; they should be linked to a superseding decision. — [Fowler bliki: ArchitectureDecisionRecord](https://www.martinfowler.com/bliki/ArchitectureDecisionRecord.html) (via search summary)
- *Clean Code* "Journal Comments": "Today we have source code control systems, we don't need this type of logs." "Nonlocal Information": "Don't offer systemwide information in the context of a local comment." — [Clean-Code-Notes](https://github.com/JuanCrg90/Clean-Code-Notes)
- Fluri et al. 2009: API changes and their comments "do not co-evolve but get re-documented in a later revision". This is evidence that documentation away from the change site lags behind it. — [Fluri et al., SQJ 2009](https://doi.org/10.1007/s11219-009-9075-x) (abstract via search)
- This repo already has the ADR/reference layer the rule assumes. `AGENTS.md` points to `docs/adr/` for rationale and `docs/reference/` for contracts, which are to be edited "in the same PR as the code they describe". — `/home/user/shiro-mlops/AGENTS.md`

### Inferences
- Division of labour consistent with both the rule and the tradition:
  - ADR: architecture-level why, with alternatives and consequences, immutable.
  - Reference docs: current contracts.
  - Commit/PR message: change-level why, the history of a diff.
  - In-code comments: only what must be seen *at the point of change* to avoid breaking things (header invariants, why-not).
- The rule removes only the duplicated copies, which is defensible. The risk is in the word "unnecessary". Knowledge that lives *only* in commit history or an ADR is non-local. Readers, human or agent, encounter it only if they think to run `git log`/`git blame` or open the ADR. Chesterton's-fence knowledge in particular must stay local.
- The two arguments trade off as follows. "Single source of truth" minimizes divergence; this is the *Clean Code*/PEP 8 concern about stale comments. "Locality" minimizes the chance that the right knowledge is missed at edit time; this is Ousterhout's concern. The rule resolves the conflict by allowing local text only where missing it would cause a breaking change. A why-not comment can also point to the ADR or issue instead of restating it, giving locality by reference.

## Q6. Style guides: Google Python, PEP 8 / PEP 257, Linux kernel, Go doc comments

### Takeaway
Every major style guide agrees with the rule on banning narration ("never describe the code", "NEVER try to explain HOW", no signature-reiterating docstrings). Every one of them **requires** function-level documentation for public or exported APIs, which the rule does not allow, and several define machine-read conventions (`__doc__`, go doc, `Deprecated:`). The Linux kernel guide is closest in spirit: no comments inside function bodies, a comment at the head of each function saying what it does "and possibly WHY". But it puts that header at function level, not only module level.

### Cited Findings
- **Google Python Style Guide §3.8.3:** "A docstring is mandatory for every function that has one or more of the following properties: being part of the public API; nontrivial size; non-obvious logic." "A docstring should give enough information to write a call to the function without reading the function's code... a function that mutates one of its arguments as a side effect should note that in its docstring." Args/Returns/Raises sections "can be omitted in cases where the function's name and signature are informative enough that it can be aptly described using a one-line docstring." — [Google pyguide](https://google.github.io/styleguide/pyguide.html)
- **Google §3.8.5:** "The final place to have comments is in tricky parts of the code. If you're going to have to explain it at the next code review, you should comment it now." "On the other hand, never describe the code. Assume the person reading the code knows Python (though not what you're trying to do) better than you do." Its *good* example includes `if i & (i-1) == 0:  # True if i is 0 or a power of 2.` Google also requires "Every file should contain license boilerplate" and "Files should start with a docstring describing the contents and usage of the module", and its TODO rule says "A bug reference is preferable". — [Google pyguide](https://google.github.io/styleguide/pyguide.html)
- **PEP 8:** "Comments that contradict the code are worse than no comments. Always make a priority of keeping the comments up-to-date when the code changes!" "Write docstrings for all public modules, functions, classes, and methods. Docstrings are not necessary for non-public methods, but you should have a comment that describes what the method does." — [PEP 8](https://peps.python.org/pep-0008/)
- **PEP 257:** "The one-line docstring should NOT be a 'signature' reiterating the function/method parameters (which can be obtained by introspection)." Yet: "all functions and classes exported by a module should also have docstrings", and "The docstring for a function or method should summarize its behavior and document its arguments, return value(s), side effects, exceptions raised, and restrictions on when it can be called (all if applicable)." The docstring "becomes the `__doc__` special attribute of that object." — [PEP 257](https://peps.python.org/pep-0257/)
- **Linux kernel coding style §8:** "Comments are good, but there is also a danger of over-commenting. NEVER try to explain HOW your code works in a comment". "Generally, you want your comments to tell WHAT your code does, not HOW." "try to avoid putting comments inside a function body"; "put the comments at the head of the function, telling people what it does, and possibly WHY it does it." Kernel-doc is required for kernel API functions. Also: "It's also important to comment data, whether they are basic types or derived types." §6: "Functions should be short and sweet, and do just one thing." — [kernel coding-style.rst](https://github.com/torvalds/linux/blob/master/Documentation/process/coding-style.rst) ([rendered](https://docs.kernel.org/process/coding-style.html))
- **Go Doc Comments:** "Every exported (capitalized) name should have a doc comment." These comments are consumed by `go doc`, pkg.go.dev/pkgsite and the gopls language server in IDEs. "A type's doc comment should explain what each instance of that type represents or provides." "By default, programmers should expect that a type is safe for use only by a single goroutine at a time. If a type provides stronger guarantees, the doc comment should state them." "Special cases can be particularly important to document" (`math.Sqrt` example). "Paragraphs starting with `Deprecated: ` are treated as deprecation notices." — [go.dev/doc/comment](https://go.dev/doc/comment)

### Inferences
- **Agreements:** PEP 257's ban on signature-reiterating docstrings is almost word for word the rule's "docstrings repeating signatures". Google's "never describe the code" and the kernel's "NEVER... explain HOW" are the rule's ban on narration. The kernel's "no comments inside function bodies; split complex functions instead" is the rule's "small functions over comments".
- **Disagreements:**
  - All four guides mandate docs for public/exported functions. Google's test is semantic ("enough information to write a call... without reading the function's code"), and the rule's "names/types/tests suffice" bet is the opposite.
  - Google's good inline example (`# True if i is 0 or a power of 2.`) is a "what" comment the rule would replace with a named helper. This is defensible, but it shows the rule is stricter than Google.
  - Go's concurrency-safety and special-case statements are runtime-behaviour descriptions. The rule says these "follow the same rules", so they survive only if they can be framed as header invariants.
- Google's "if you'd have to explain it at the next code review, comment it now" is a practical operationalization of the rule's why-not trigger, and the two are compatible.

## Q7. Empirical research: comment–code co-evolution and rot, effects on comprehension, self-admitted technical debt, and comment taxonomies (what vs why)

### Takeaway
The evidence cuts both ways. Comments measurably help human comprehension in controlled experiments (Woodfield 1981; Tenny 1988). Comments, especially API/interface docs and newly added code, often lag or go stale (Fluri 2007/2009; Wen 2019). TODO/debt comments are common and frequently linger (Potdar & Shihab 2014). That supports the rule's suspicion of redundant comments and its "delete with the code" coupling. It does not support deleting interface semantics, which is the information the comprehension experiments show readers benefit from.

### Cited Findings
- **Fluri, Würsch & Gall, WCRE 2007** ("Do Code and Comments Co-Evolve?"; ArgoUML, Azureus, Eclipse JDT Core):
  - 97% of comment changes occurred in the same revision as the associated code change.
  - "newly added code - despite its growth rate - barely gets commented".
  - Class and method declarations are the most commented.
  - A citing paper summarizes that 23%, 52% and 43% of all comment changes (ArgoUML, Azureus, JDT Core) were triggered by source changes.
  — [WCRE 2007 record](https://bibtex.github.io/WCRE-2007-FluriWG.html); [arXiv 2409.10781 (citing summary)](https://arxiv.org/pdf/2409.10781) (abstract/summary via search)
- **Fluri, Würsch, Giger & Gall, Software Quality Journal 2009** (8 systems): in 6 of 8 systems, code and comments co-evolve in 90% of cases; "API changes and comments do not co-evolve but get re-documented in a later revision." — [SQJ 2009](https://doi.org/10.1007/s11219-009-9075-x) (abstract via search)
- **Wen, Nagy, Bavota & Lanza, ICPC 2019**, "A Large-Scale Empirical Study on Code-Comment Inconsistencies" (pp. 53–64, DOI 10.1109/ICPC.2019.00019): mines the complete change history of 1,500 Java GitHub projects (described elsewhere as ~1.3 billion AST-level changes). It also manually analyses 500 commits to build a taxonomy of code-comment inconsistencies fixed by developers, and reports which kinds of code change tend to trigger comment updates. Later work cites it as evidence that developers often fail to update comments right after code changes. — [ICPC 2019 record](https://bibtex.github.io/ICPC-2019-WenNBL.html); [USI PDF](https://www.inf.usi.ch/faculty/lanza/PUBS/P/Wen2019a.pdf) (not fetchable here; via search summary); [arXiv 2010.01625 citing it](https://arxiv.org/pdf/2010.01625v2.pdf)
- Follow-on work exists on the bug impact of comment inconsistency ("Investigating the Impact of Code Comment Inconsistency on Bug Introducing", arXiv 2409.10781). Another paper detects stale function references in comments ("We Must Have Missed This Comment: Detecting and Repairing Stale Function References in Linux Kernel Comments", arXiv 2608.03734). — [arXiv 2409.10781](https://arxiv.org/pdf/2409.10781); [arXiv 2608.03734](https://arxiv.org/pdf/2608.03734) (titles only via search; contents not verified)
- **Woodfield, Dunsmore & Shen, ICSE 1981** ("The Effect of Modularization and Comments on Program Comprehension", pp. 215–223): 48 experienced programmers, 8 versions of a program (4 modularization types × with/without comments), 20-question comprehension quiz. Commented versions scored higher, and the abstract-data-type modularization did best. — [ICSE 1981 record](https://bibtex.github.io/ICSE-1981-WoodfieldDS.html) (via search summary)
- **Tenny, IEEE TSE 1988** ("Program Readability: Procedures Versus Comments"): a 3×2 factorial design on a PL/I program (procedure format none/internal/external × comments absent/present). The most and least readable versions were both procedureless, with and without comments respectively. Procedures had little effect, possibly because the program was small; comments improved readability, especially without procedures. — [Tenny 1988](https://typeset.io/pdf/program-readability-procedures-versus-comments-1dkd5enuki.pdf); [record](https://www.bohrium.com/paper-details/program-readability-procedures-versus-comments/812461770831560704-2431) (via search summary)
- **Potdar & Shihab, ICSME 2014** ("An Exploratory Study on Self-Admitted Technical Debt"; Eclipse, Chromium OS, Apache httpd, ArgoUML):
  - SATD comments appear in 2.4%–31% of files.
  - Only 26.3%–63.5% of SATD is removed after introduction.
  - More experienced developers introduce most SATD.
  - Time pressure and code complexity do not correlate with the amount.
  - A replication by Bavota & Russo on more projects reports ~57% removed, ~63% of which were self-removed.
  — [ICSME 2014 record](https://bibtex.github.io/ICSME-2014-PotdarS.html); [researchr](https://researchr.org/publication/PotdarS14); [arXiv 2101.03730 citing](https://arxiv.org/pdf/2101.03730) (via search summary)
- **Pascarella & Bacchelli, MSR 2017** ("Classifying Code Comments in Java Open-Source Software Systems", pp. 227–237): 6 Java OSS systems, >2,000 comments manually classified into a taxonomy, with category frequencies measured. **Pascarella, Bruntink & Bacchelli, EMSE 24:1499–1537 (2019)** extends this to 14 open and closed source Java projects and >40,000 comment lines, with ML line-level classification. A prior taxonomy they cite has 7 high-level categories: COPYRIGHT, HEADER, MEMBER, INLINE, SECTION, CODE, TASK. — [TU Delft MSR 2017](https://research.tudelft.nl/en/publications/classifying-code-comments-in-java-open-source-software-systems); [TU Delft EMSE 2019](https://repository.tudelft.nl/record/uuid:9056648d-2b74-4606-8df0-4742fbce9a86) (via search summary)

### Inferences
- Fluri's "API changes and comments do not co-evolve but get re-documented in a later revision" is the strongest empirical support for the rule's distrust of interface docstrings. Interface docs are where lag concentrates. It is also evidence that the docs were considered worth re-documenting, so developers valued them.
- The "97% same-revision" figure means most comment updates that do happen are made with the code. The rule's "delete with the protected code" coupling fits this natural workflow. The risk lies in comments that should have changed but did not, which Wen 2019 studies.
- Old comprehension experiments (FORTRAN/PL/I-era, small programs, human subjects) show that comments help comprehension. They do not separate "what" comments from "why" comments, and they do not test modern naming or typing. They therefore neither confirm nor refute the rule's claim that names/types/tests can replace "what" comments.
- Potdar & Shihab show that TODO/debt comments are widespread and long-lived. The rule's silence on TODO means either losing that signal or pushing it entirely into issues. The repo's `TODO(#123)` convention is a middle ground: an issue-linked marker, consistent with Google's "bug reference is preferable".
- The research taxonomies (license/copyright, header, member, inline, task, commented-out code) show that real-world comment content spans far more than "why" and "invariants". A strict application of the rule would delete or relocate a large share of existing comments. The exact share depends on Pascarella's category frequencies, which I could not verify.

- **Wen et al. 2019:** I could not obtain the paper's quantitative findings (rates of inconsistency, taxonomy categories and percentages); the USI PDF was blocked.
- **Pascarella & Bacchelli:** I could not obtain per-category frequencies (for example, the share of "Summary" versus "Rationale" comments). From recollection, the taxonomy includes categories such as Summary, Expand, Rationale, Deprecation, Usage, Exception, TODO, Incomplete, Commented code, Directive, Formatter, License, Ownership, Pointer, Auto-generated and Noise, with Summary/Usage-type comments dominant. ## Q8. What risks does traditional wisdom flag in an aggressive comment-deletion rule?

### Takeaway
Traditional sources flag eight risks: (1) loss of interface semantics that signatures do not carry; (2) breaking tool chains that consume docstrings; (3) dropping legally required headers; (4) losing TODO/debt signals; (5) pushing knowledge into non-local places (commit history, ADRs) where it is missed; (6) prose "天條" gaining authority without verifiability; (7) the opposite failure, mandated boilerplate headers ("Mandated Comments"); and (8) over-long names as comment substitutes.

### Cited Findings
- **Interface semantics.** "Sometimes the signature of a method... contains all the information needed to use it, but this is pretty rare." Re-deriving interfaces from code leads to "probably making mistakes along the way" (Ousterhout). Google's test for a docstring: "enough information to write a call to the function without reading the function's code". — [aposd-vs-clean-code](https://github.com/johnousterhout/aposd-vs-clean-code); [Google pyguide](https://google.github.io/styleguide/pyguide.html)
- **Tool chains.** Sphinx autodoc's purpose is to "Include documentation from docstrings" and "pull in documentation from docstrings in a semi-automatic way". Python docstrings become `__doc__` (PEP 257). Go doc comments feed `go doc`, pkgsite and gopls IDE hovers, and `Deprecated:` paragraphs are machine-recognized. — [Sphinx autodoc](https://www.sphinx-doc.org/en/master/usage/extensions/autodoc.html); [PEP 257](https://peps.python.org/pep-0257/); [Go Doc Comments](https://go.dev/doc/comment)
- **Legal headers.** *Clean Code* allows legal comments ("copyright and authorship statements are necessary and reasonable"), and Google requires "license boilerplate" in every file. — [Clean-Code-Notes](https://github.com/JuanCrg90/Clean-Code-Notes); [Google pyguide](https://google.github.io/styleguide/pyguide.html)
- **TODO/debt.** *Clean Code* allows TODO comments. Google prefers TODOs with a bug reference. SATD is present in up to 31% of files, and much of it is never removed. — [Clean-Code-Notes](https://github.com/JuanCrg90/Clean-Code-Notes); [Google pyguide](https://google.github.io/styleguide/pyguide.html); [Potdar & Shihab 2014](https://bibtex.github.io/ICSME-2014-PotdarS.html)
- **Staleness versus absence.** PEP 8: "Comments that contradict the code are worse than no comments." Ousterhout: "missing comments are a much greater cause of lost productivity than erroneous or unhelpful comments." Martin believes the reverse ("bad comments cost more time than good comments save"). — [PEP 8](https://peps.python.org/pep-0008/); [aposd-vs-clean-code](https://github.com/johnousterhout/aposd-vs-clean-code)
- **Mandated boilerplate.** "It is just plain silly to have a rule that says that every function must have a javadoc"; "Plopping in a comment just because you feel you should or because the process requires it, is a hack." — [Clean-Code-Notes](https://github.com/JuanCrg90/Clean-Code-Notes)
- **Long names.** Ousterhout: "super-long names are awkward and hard to understand, and... it would be better to use shorter names supplemented with comments." Martin: "I prefer long names to comments. I don't trust comments to be maintained, nor do I trust that they will be read." — [aposd-vs-clean-code](https://github.com/johnousterhout/aposd-vs-clean-code)
- **Trivial-looking justifications.** Writing them anyway "provides a way to know that there are no *extra* implicit constraints" (kernel Rust guidelines). — [kernel rust coding-guidelines](https://github.com/torvalds/linux/blob/master/Documentation/rust/coding-guidelines.rst)

### Inferences
- **Agreement.** The rule agrees with nearly all sources on deleting narration, signature restatement, journals, bylines, commented-out code and position markers. Its why-not category matches Chesterton's fence, Atwood's "why", *Clean Code*'s intent/warning/amplification, Google's "tricky parts" and the Rust SAFETY convention. Its "name the protected code, delete with it" clause is stricter and more maintainable than anything in the classic guides, and resembles the clippy lint pair.
- **Disagreement.** The rule's biggest departure from tradition is having no function-level interface-comment category. It is also silent on legal headers, TODOs, data/field semantics (units, sentinels, ranges; Kernighan & Pike, the kernel's "comment data") and tool-consumed public docs. These are the areas where every style guide and both Martin (for public APIs) and Ousterhout (for all interfaces) disagree with it.
- **Risks specific to agents** that the classic wisdom implies:
  - (a) An agent that sees no why-not comment may "simplify" deliberate code.
  - (b) An agent that sees a confidently stated header "天條" will treat it as truth even when stale. Martin's "potential misinformation" warning applies more strongly, because agents tend to follow instructions in context.
  - (c) An agent re-deriving interfaces each session pays Ousterhout's error cost, not just his time cost.
  - (d) If the agent also *writes* the code, it may produce the kind of comments the rule bans, so the rule needs enforcement (lint or review), not just exhortation.
- **Possible mitigations** consistent with tradition:
  - Exempt license/SPDX headers and issue-linked `TODO(#n)` markers.
  - Permit function-level docstrings for public or tool-rendered APIs, limited to semantics that names and types do not carry (PEP 257 and Google already forbid signature restatement).
  - Back each header invariant with an executable check and cite that check in the header.
  - Give why-not comments a greppable tag naming the protected symbol, so stale ones can be detected (cf. clippy, and the arXiv 2608.03734 work on stale function references).

### Gaps
- I found no empirical study that directly measures the effect of an aggressive comment-deletion policy on later defect rates or on LLM-agent edit correctness. Agent-specific evidence is outside this note's scope and is expected from the parallel researcher.
